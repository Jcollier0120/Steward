# Accelerators: the NPU, graphics cards and the CPU

> **This page's home is the Steward's kit**, its `spec` part: `kit/spec/ACCELERATORS.md` in the Steward's repository, and `src/kit/spec/ACCELERATORS.md` in every agent that takes the part. It was Manor's `docs/ACCELERATORS.md`. A change to the contract is a kit change: made here, released as a kit version, and taken by every agent from that release. Since kit 2.0.0 its rules are the kit's core (`core/accelerators.js`, `core/ids.js`, `core/messages.js`): reading and checking the config, the order, the candidates and the pick, the failure markers, the game check, the ids and the messages, with the timings and limits of [rules.json](rules.json). The kit's node part (`node/accelerators.ts`, `node/npu.ts`) and dotnet part carry them out, and [accelerator-vectors.json](accelerator-vectors.json) holds the cases every implementation runs. The queue it uses is [NPU-QUEUE.md](NPU-QUEUE.md), beside this page.

The manor's agents ask a model to label, name, summarise or describe; code still decides everything (house rule 1). Until now every model ran on one Hexagon NPU, through one lock and one line. This is how the same agents run on any PC: a Snapdragon laptop's NPU, a gaming desktop's graphics cards (one or several), or only its processor. Every agent follows it, so each still works on its own.

The model is Heiward's: list the devices, recommend one, let the person choose, check it before committing to it, fall back when it fails, and say where the work actually ran. Heiward's graphics-card choice is the reference for naming and choosing cards.

## Accelerators and their ids

An **accelerator** is a device that runs the manor's models, behind a model server:

| Kind | Id | Name |
|---|---|---|
| The NPU | `npu` | Its device name as Windows lists it, kept in full in hardware.json ("Snapdragon X2 Elite Extreme - X2E94100 - Qualcomm Hexagon NPU") and shown by its model, "Qualcomm Hexagon" (Manor shows the same) |
| A graphics card | `gpu-` + its name in lowercase, each run of other characters a dash, none at either end, e.g. `gpu-nvidia-geforce-rtx-4090` | DXGI's description, as Heiward lists it: Windows' software adapters (Basic Render, Remote Display, Hyper-V) left out, and a second card of the same name `… #2` (id `…-2`). Shown as Manor shows it ("Qualcomm Adreno X2-90"); the id is made from the name as DXGI gives it (`gpu-qualcomm-r-adreno-tm-x2-90-gpu`) |
| The processor | `cpu` | The processor's name as Windows gives it, shown by its model: "Qualcomm Oryon" for "Snapdragon(R) X2 Elite Extreme - X2E94100 - Qualcomm Oryon(TM) CPU" |

Names, not DXGI's numbers, identify cards: DXGI's numbers can change from boot to boot. A card's DXGI number and LUID are looked up when a server starts.

**A name is what the PC calls the device, never a setting** (kit 2.27.0). It comes from `hardware.json` (What this PC has, below): the NPU's from its `npuName`, a card's from the card in `cards` whose name gives the entry's id, the processor's from its `cpuName`. Without one (no hardware.json yet, a card it doesn't list, an NPU on a PC without one) it is the kind's: "NPU", "Graphics card", "Processor". `config.json` keeps no name: one an older file's entry carries is ignored, and dropped when the file is next written; setup writes none, and no Settings page offers one to edit. Each is shown as Manor shows it (the core's `deviceName`): (R), (TM) and (C) taken out and its spaces collapsed; a "<chip> - <part number> - <model>" name only its model; and no last "NPU", "CPU" or "GPU", which its kind says beside it. hardware.json keeps the name in full, and an id never changes with it. The core's `acceleratorName(kind, id, hw)` is the rule.

## What this PC has

What decides whether a model runs on the NPU is the PC, never the model: any model can run on any accelerator, so no model name or server address is ever read as a sign of one. Detection asks Windows which Neural processors it lists (the `ComputeAccelerator` device class: Qualcomm's Hexagon, Intel's AI Boost, AMD's XDNA, each with its maker, generation and driver, and whether the manor can run models on it: NPU-VENDORS.md, since kit 2.31.0) and which graphics cards DXGI has, and its answer is kept in `hardware.json` (Shared files, below): `{ "at": "<ISO time>", "npu": false, "cards": [{ "name": "NVIDIA GeForce RTX 4080 SUPER", "memoryGb": 16 }], "cpuName": "AMD Ryzen 9 7950X 16-Core Processor" }`, with `"npuName"` beside `"npu": true` on a PC with one (`"Snapdragon X2 Elite Extreme - X2E94100 - Qualcomm Hexagon NPU"`). These names are every accelerator's (Accelerators and their ids, above). It's written only when both questions were answered (an NPU found, or none for certain, and the cards listed); setup writes it, and the keeper asks again when it's a day old, at once when it says there's an NPU but not its name (a file from before kit 2.27.0), and after an hour when it lacks the processor's.

On a PC known to have no NPU, an entry said to be the NPU (an `npu` id, an old config's `device: "Npu"`, or an old endpoint that names no device) runs on what the PC has instead:
- its one graphics card, by that card's name and memory;
- "Graphics card" when it has several (which one isn't known);
- the processor when it has none.

It takes that kind, that name and the id it gives, whatever the entry carried, and goes after the others: a card's own entry of the same id comes first, and gets the servers it lacked from it. An old config's GenieX quirks go (GenieX runs only on an NPU), and `acceleratorOrder` follows the new id. The config's problems say so. With an NPU, or with no hardware.json, a config is taken at its word.

A note that says nothing of where it was written (one kept from before accelerators) is "from a local model", never "the NPU".

## Where they're kept

The accelerators are in **their own `config.json`, in a folder Manor owns**: `%USERPROFILE%\.manor\accelerators\config.json` (kit 2.31.0; `MANOR_HOME`'s `accelerators`, `ACCELERATORS_HOME`, or `ACCELERATORS_CONFIG` name another; a scratch `REEVE_HOME` or `REEVE_CONFIG` keeps one file there, as before). A household gets working models without hiring Reeve: Manor's Set up local AI writes it. Whoever keeps the model servers owns it: **the Smith** where it is installed (`%USERPROFILE%\.smith\app`), else Reeve, else Manor's own setup. The keeper detects them, sets up their servers, and offers them on its Settings page; nobody edits the file by hand. It holds the keeper's keys, `accelerators`, `acceleratorOrder`, `workOrder` (kit 2.111.0), `npuIdleStopMinutes` and `gpuIdleStopMinutes` (the kit's `accelerator-config.ts`, `KEEPER_KEYS`), and an older config's single endpoint and `requestTimeoutMs`. Each write keeps every other key, and is refused when the file changed since it was read.

**Moving from Reeve's config.json.** Until kit 2.31.0 they were in Reeve's `%USERPROFILE%\.reeve\config.json` (or `.npu-agent`'s), beside Reeve's own keys. The first time the keeper or its Settings page reads the accelerators' own file and it isn't there, it is written with a copy of their keys from Reeve's file (`migrateAcceleratorConfig`), with `movedFrom` and `movedAt` saying so; a person's working entries are copied word for word. Reeve's file is never changed by the move. Until then, every agent reads Reeve's (`readableConfigFile`: the accelerators' own when it exists, else Reeve's). After it, each write of the keeper's keys is mirrored back into Reeve's file when it is there (`mirrorToLegacy`), so an agent on an older kit, and Reeve before he takes the new one, still read the same accelerators; Reeve's own keys are never touched. A change Reeve's older Settings page makes in his own file after the move isn't read by the new kit: make it on the Smith's page, or Manor's.

llama.cpp's builds and the models go into the accelerators' folder (`servers\`, `models\`), as do the NPU servers setup unpacks; a PC set up before kit 2.31.0 keeps `%USERPROFILE%\.reeve\servers` and `models`, where they already are (`toolsHome`). The keeper's log is `servers\logs\reaper.log` there. The locks and the shared files below stay in `%USERPROFILE%\.npu-agent\`, where Heiward's released builds look for the NPU's lock.

```json
{
  "accelerators": [
    {
      "id": "gpu-nvidia-geforce-rtx-4090", "kind": "gpu", "memoryGb": 24,
      "slots": 2, "maxContextTokens": 16384,
      "chat":   { "baseUrl": "http://127.0.0.1:18191", "model": "qwen3-vl-2b-instruct",
                  "startCommand": ["%USERPROFILE%\\.manor\\accelerators\\servers\\llama.cpp\\llama.cpp-b11734-cuda-12.4-x64\\llama-server.exe", "--port", "18191", "--device", "CUDA0", "..."] },
      "vision": { "model": "qwen3-vl-2b-instruct" },
      "embed":  { "baseUrl": "http://127.0.0.1:18192", "model": "qwen3-embedding-0.6b", "startCommand": ["..."] },
      "quirks": []
    },
    {
      "id": "npu", "kind": "npu", "slots": 1, "maxContextTokens": 2400,
      "chat":   { "baseUrl": "http://127.0.0.1:18181", "model": "unsloth/Qwen3-VL-2B-Instruct-GGUF:Q4_0", "startCommand": ["%LOCALAPPDATA%\\GenieX CLI\\geniex.exe", "serve", "--skip-update", "..."] },
      "vision": { "model": "unsloth/Qwen3-VL-2B-Instruct-GGUF:Q4_0", "pictureTokens": 1024 },
      "embed":  { "baseUrl": "http://127.0.0.1:18182", "model": "qwen3-embedding-0.6b-gguf", "startCommand": ["..."] },
      "quirks": ["prefix-leak", "image-path"]
    }
  ],
  "acceleratorOrder": "auto"
}
```

- `slots`: how many requests it serves at once (llama-server's `--parallel`). The NPU has 1.
- `maxContextTokens`: the most a request may be, prompt and answer, by the kit's pessimistic estimate. The NPU keeps 2,400: an ~8K-token prompt bluescreened this laptop (bug check 0x18B). A graphics card's comes from its memory and the model's context. A request over every candidate's cap is refused before it's sent, as now.
- `chat`, `vision`, `embed`: what it serves, each an OpenAI-compatible endpoint (`/v1/chat/completions`, `/v1/embeddings`), its model, and the command that starts its server when it isn't running (detached, hidden, as GenieX is started now). Leaving one out means it doesn't serve that kind.
- `rerank` (kit 2.41.0): a reranker, llama.cpp's server started with `--reranking` (`/v1/rerank`: a question and documents in, each document's relevance out), set up only when asked for (`--serve rerank`). It is an add-on, not routed work: no agent's chat, vision or embedding requests go to it, and the core doesn't read it. An agent that wants one (Reeve's search) finds it with `endpointFor(a, 'rerank')`. A Snapdragon X2's NPU reranks (kit 2.100.0): its embedding server's llama.cpp started again with `--reranking` on port 18185, in the NPU's turn (NPU-VENDORS.md, Reranking on the Hexagon); no other NPU's servers rerank.
- `quirks`, per server: `prefix-leak` (GenieX v0.7.0: each request starts with a nonce), `image-path` (the server reads a local image path; otherwise images are sent as `data:` URLs), `sides-of-32` (FastFlowLM 1.0.7 and 1.0.10 misread a picture 720 px tall or less with a side of a whole number of 32 px: the kit's `fitPicture` makes such a side a pixel longer first, NPU-VENDORS.md).
- `vision.pictureTokens` (kit 2.80.2): the most tokens a picture may be on a server that reads it at its own size, a token per 32 × 32 px (Qwen3-VL through GenieX's llama.cpp plugin), a whole number from 64 to 4,096. The kit redraws a larger picture to fit (`fitPicture`) and counts each picture on that server as this many against its cap, in place of the rules' `imageTokens` (400). Setup writes 1,024 for the X2's Qwen3-VL-2B (NPU-VENDORS.md); without it a picture goes at its own size and counts 400.
- `acceleratorOrder`: `"auto"`, or a list of ids, first preferred. Auto puts the NPU first, since it does model work without the processor or a graphics card; then graphics cards with 2 GB or more of their own memory, by memory; then graphics that share the PC's memory; then the CPU.
- `workOrder` (kit 2.111.0): each work's own order on this PC, `{ "vision": { "devices": ["gpu", "npu", "cpu"] }, … }`, the kinds of device for `chat`, `vision` and `embed`, first preferred, each at most once; `runningFirst`, a device whose server is up first; and `batchAt`, a whole number, 2 or more, from which many of the work waiting the order is kept whoever's server is up. Setup writes it from the NPU's generation (`npu-vendors.json`'s `order`, measured: NPU-VENDORS.md, Each work's order on a generation), and nobody else; the keeper's look (npu-refresh.ts) brings it to a later kit's once for each kit version, so a PC set up earlier needn't be set up again (kit 2.135.1). A card it puts first for a work it doesn't serve yet gains that work at the keeper's look (kit 2.135.2, set-up-again.ts' `orderAdds`). No generation's order has `runningFirst` or `batchAt` since kit 2.135.1. It counts only with `acceleratorOrder` "auto": a person's list is kept for every work. A work written wrong is left out, and the check names it.
- An old config with only `chatEndpoint` (and `visionModel`, `embedEndpoint`, `npuMaxContextTokens`) still works: it is read as one accelerator per device it names, `npu`, `gpu-graphics-card` or `cpu`.
- The kind comes from the id, and the name from the PC (Accelerators and their ids, above): an entry has no `name`, and one it has is ignored. The NPU always has one slot; the others at most 16.
- `enabled: false` keeps an entry but sends it nothing. `%VAR%` in a `startCommand` is expanded.
- Since kit 2.31.0, an endpoint may carry its own `maxContextTokens` (a cap for that kind, lower or higher than its accelerator's: the core's `capFor`) and `env` (what its server's environment needs, set over the starter's when its `startCommand` starts it, each `%VAR%` expanded: OpenVINO Model Server's `PYTHONHOME` and `PATH`); an accelerator may carry `timeouts` (`requestBaseMs`, `requestPerTokenMs`, `coldLoadMs`, each in place of the rules' for its requests). Setup writes them for an NPU from `npu-vendors.json`, and a graphics card's or the processor's embedding server gets a `maxContextTokens` of 1,365 (setup's `EMBED_CAP`): it starts with `-c 4096 -ub 512`, and an input under that cap is at most 4,095 characters, which fit even at a token a character. A config set up before keeps its `-c 8192 -ub 2048` and no cap until it's set up again.
- An endpoint whose server runs on another device than its accelerator's may carry `turn`: that device's id (a graphics card's, `gpu-…`, or `cpu`), whose lock and line its requests take (the core's `turnOf`; the lock and the line, below). The NPU 3720's embedding server runs on the processor's graphics (`--target_device GPU`), so setup writes its embeddings `turn` as the id of the Intel graphics that shares the PC's memory, and they answer beside the NPU's chat instead of waiting for it ([NPU-VENDORS.md](NPU-VENDORS.md#the-npu-3720s-embeddings-in-the-graphics-turn)). The NPU's own id, or anything that isn't an id, isn't a turn: the entry is read without it, and the check names it. A vision model on its chat endpoint's server takes chat's. Everything else stays the accelerator's: its failure marker, its cap, its name in an answer.
- An endpoint may carry its own `timeouts` too (the same three), each over its accelerator's for that kind's requests alone (the core's `timeoutsFor`), on its own server or its chat endpoint's. Setup writes vision's on Intel's integrated graphics, whose pictures are encoded on the processor (where a card's vision encoder runs, below). An older kit reads the entry without them.

Setup (Manor's Set up local AI, `smith accelerators setup` and the Set up button on the Smith's Settings page; Reeve's where there is no Smith: the kit's `setup.ts`) sets the NPU up first, with its maker's server (NPU-VENDORS.md: downloaded, checked against its pinned SHA-256, installed for the user, its models pulled, and its entry written only after a test request), then downloads llama.cpp's build for each card, ggml-org's own signed by the manor (below), into the tools home's `servers\llama.cpp\` (the one build the kit pins, below; on the Adreno none before b11715, setup.ts' `OLDEST_BUILD`), and the models, as GGUF files, from Hugging Face into its `models\`, each at the commit the kit pins and checked against its pinned SHA-256 (below): on every card and on the processor one Qwen3-VL-2B-Instruct for chat and vision (below; on cards with memory of their own from kit 2.89.0, which before it had Qwen3-4B-Instruct-2507 for chat beside Qwen3-VL-4B-Instruct for vision); Qwen3-Embedding-0.6B for embeddings everywhere; and, when asked for, Qwen3-Reranker-0.6B (llama.cpp's own GGUF, ggml-org's) for reranking. A reranker is set up beside what its accelerator already serves, on a port of its own, and setting the others up again keeps it; a graphics card or the processor can serve one. It says how much it will download and asks first. It matches each card to llama-server's device by name (`llama-server --list-devices`), and gives each server its own port from 18191 up.

**Where a card's vision encoder runs.** A vision server is llama-server with its model's projector (`--mmproj`), which encodes each picture into tokens before the model reads them; on a card both run on the card. Intel's integrated graphics (a card whose id is `gpu-intel-…`, with under 2 GB of its own, on the Vulkan build) encode on the processor instead (`--no-mmproj-offload`, setup.ts' `encodesOnProcessor`), and the model stays on the graphics. On a Core Ultra 5 225U's Intel Graphics (driver 32.0.101.8831, llama.cpp b11624 and b11669, 2026-10-15) the encoder lost the device (`ggml_vulkan: device lost`, no display driver reset) at the server's warm-up, so the server exited as it started, in every one of the Smith's audits that day. So such a card's vision server also caps each picture at 1,024 tokens (`--image-max-tokens 1024`, setup.ts' `PICTURE_CAP`), and its vision endpoint has its own `timeouts`, `{ "requestBaseMs": 90000 }` (`VISION_ON_PROCESSOR_TIMEOUTS`): a background request may take 90 s and the rules' 0.3 s for each token it may answer. The rules' 15 s would fail Reeve's screens' 4-token questions about a phone's screenshot (16.2 s in all), and a request that times out marks its card failed for 10 minutes, its chat too. Its chat keeps the rules'. Any endpoint may have its own `timeouts`, over its accelerator's, each one it gives (the core's `timeoutsFor`), validated as an accelerator's are. Measured on the same PC through the kit's own start and requests (`ensureServer`, `visionBody`), b11669, at below-normal priority on a busy PC (2026-10-15), each picture's first question:

| A picture | Uncapped | Capped at 1,024 tokens |

Every answer was right both ways: a bold heading quoted word for word, a count of suggested tasks, the window's title, the percentage beside "Context", the clock's time. A question again on the same picture took 0.8 to 1.7 s, as llama-server keeps a picture it has encoded. So the cap holds a picture to about 30 s whatever its size, at no cost to these answers; a big screen's smallest text may not survive it, though none of the questions asked found that. With the cap and its own time, the slowest first question measured has three times what it took.

A PC set up before gets the flag, the cap and the time at the keeper's next look (setup.ts' `refreshCardVision`): once for each kit version, recorded in `card-refresh.json` beside config.json. It adds each one missing from such a card's llama-server vision (the flag after the projector, the cap after the flag), so a cap or time a person set stays theirs; it leaves alone a command that keeps its encoder on the card (`--mmproj-offload`), and starts and stops nothing. A person who takes one out keeps it out until the next kit. Intel's cards with memory of their own (Arc A and B) and other makers' integrated graphics weren't measured, and keep their encoder on the card, uncapped, on the rules' time.

**No RAM cache of earlier prompts.** llama-server keeps the states of earlier prompts in the PC's memory, up to 8,192 MiB for each server by default (`--cache-ram`), beside what its card holds, so that a later prompt starting the same way skips reading that start again. The manor's agents share little more than a short system prompt, and each slot still reuses its own last prompt without it. Setup writes `LLAMA_ARG_CACHE_RAM=0` into the `env` of every llama-server it sets up on a card or the processor (setup.ts' `NO_RAM_CACHE`): in the environment, because a build from before the flag ignores it, where it would refuse the flag and not start. On a Core Ultra 5 225U's Intel Graphics (b11669, 2026-10-16), 34 of the manor's kind of requests through the chat server, the same ones each way:

|---|---|---|---|
| As set up before | 4.54 GB | 118 s | |
| `LLAMA_ARG_CACHE_RAM=0` | 3.59 GB | 111 s | the same |

A PC set up before gets it at the same look (`withoutRamCache`), each server at its next start. A server whose command or environment already says how much to cache (`--cache-ram`, `-cram`, `LLAMA_ARG_CACHE_RAM`) keeps it, and so does a server that isn't llama-server, an NPU's among them.

**Signed builds (kit 2.90.0).** ggml-org signs none of its llama.cpp builds, and Windows' Smart App Control blocks unsigned files it doesn't know. On 2026-10-19 it blocked `ggml-cpu-ivybridge.dll`, one of b11734's processor variants, on the gaming desktop (app-control.ts names such a block). So setup takes llama.cpp only from the releases repository's `llama.cpp-<build>` releases (setup.ts' `SIGNED_LLAMA_REPO`), and from kit 2.97.0 only the one the kit pins (below).

## The lock and the line, per accelerator

Reeve's `docs/NPU-QUEUE.md` protocol, unchanged in its rules, once per accelerator:

- Its lock folders are in `%USERPROFILE%\.npu-agent\locks\`: `<id>` for its first slot (the NPU's is `npu`, as now), `<id>.2` … `<id>.<slots>` for the others. `NPU_AGENT_NPU_LOCK` still moves the NPU's, and its folder holds the others.
- Its line is `<id>.queue`, with the same tickets, lanes, heartbeats and ages. The ticket at the head of the line takes any free slot; once it holds one, its ticket goes and the next is the head.
- A program that knows nothing of slots (Heiward, npu-embed) takes the first slot only, through the same line, and stays compatible.
- A request takes the turn of the device its server runs on: its endpoint's `turn` when it has one, else its accelerator's. The NPU 3720's embeddings take the graphics' (`<id>`, and `<id>.2` … when the graphics have an entry with more slots, else one), so a search query answers while the NPU writes, and a card entry on the same graphics shares that turn with them. The pick reads that turn's line, and a background request's back-off is that turn's. The keeper looks after such a server in that turn too, with its accelerator's idle time, and the NPU's refresh holds both turns while it changes the NPU's servers.

## Choosing an accelerator for a request

Each request, in the kit and in Reeve:

1. **Candidates**: the accelerators that serve its kind, whose cap fits it, that haven't failed in the last 10 minutes, and, for a background request, that a game isn't using (below). When every one that serves it and fits has failed, they are all candidates again, as a last resort: a PC with only the NPU isn't left without model work for 10 minutes after one hiccup.
2. **Order**: `acceleratorOrder`. With a list, the ids it leaves out follow in the auto order. **The NPU first:** when the first candidate that serves the request and fits it, in that order, is the NPU and it hasn't failed in the last 10 minutes (or every one has, the last resort), it is the only candidate. A graphics card or the processor takes a request only when the NPU can't: it doesn't serve that kind, the request is too big for it, or it failed lately. Busy, resting after a long line (a background request is then deferred), or loading its model, the NPU is waited for, never passed over. A list that puts something else first is the person's choice, and kept (the core's `candidates`, its `npuFirst`). **Each work's own order** (kit 2.111.0): with "auto", the config's `workOrder` for the request's kind puts the candidates in its devices' order first, any it leaves out after them in the auto order (the core's `workOrdered`); with its `runningFirst`, those whose server is up go first, the order kept otherwise, each looked at once before the candidates are chosen (a GET of its `/v1/models`, waiting 0.5 s at most and starting nothing: `serversUp`). With its `batchAt`, from that many of the work waiting (this request included: `waitingFor`, and the caller's `AskOptions.batch`), the order is kept whoever's server is up, so a batch starts the first device's server. **The order's first, alone** (kit 2.112.1 with `runningFirst` or a batch; kit 2.135.1 for every work order): the first in the work's order that can take the request is its only candidate, as the NPU first is. Busy, it is waited for, not passed over for a free device that spends more on the work (the owner's rule for a device merely busy). The next takes it only when that one has failed lately, is a game's, or is rested after a long line; background work longer than a line takes (`maxAhead`, 4) waits for a later round, as on the NPU. The NPU first is then the NPU first in that order. On AMD's Ryzen AI 300 every picture goes to the Radeon, whoever's server is up, and to the NPU only when the Radeon can't (the owner's ruling, 2026-10-24; until kit 2.135.1 a picture went to the NPU while only FastFlowLM was up and fewer than 4 waited); its embeddings wait for the Radeon too, rather than going to the processor (12.8 mJ a token against 44.1). Reeve's own routing reads `workOrder` too, from Reeve 0.18.63 (its `src/routing.ts`), and takes the order's first alone with `runningFirst` or a batch from Reeve 0.18.66; for every work order in a later release.
3. **Pick**: the first candidate in that order with a free slot and nobody waiting; else the one whose line is shortest, ties by order. A background request that would be fifth or later in every line is deferred, as on the NPU now. An interactive one always joins.
4. **Fallback**: when its server won't start within 30 s, refuses the connection, answers 5xx or times out, the request leaves its turn, the accelerator is marked failed (`%USERPROFILE%\.npu-agent\accelerators\<id>.failed.json`: when, and why), and the request goes once to the next candidate. A failed accelerator is tried again after 10 minutes. A timeout while the model was loading is not a failure (below): nothing is marked, and the request goes to the next candidate, or waits for a later round. On the NPU first, it waits: loading is slow, not something the NPU can't do.
5. **Where it ran**: every answer says which accelerator gave it. An agent's unverified note says so ("note from the RTX 4090, unverified").

**The graphics card beside the NPU.** Manor's Settings switch "Use the graphics card for models when there's an NPU" is saved as `"gpuWithNpu": true | false` in Manor's settings.json; on by default, and an absent key (an older Manor, or none) means on. On, a card takes only what the NPU can't (step 2). Off, on a PC whose config has an NPU that serves something (not `enabled: false`), each graphics card keeps, before step 1, only the work no enabled NPU serves (kit 2.69.0, the card on demand): for the NPU's own work it is never a candidate, not even as the fallback when the NPU fails, is busy or has a full line, and those servers aren't started. Beside a Snapdragon's NPU, which chats, sees and embeds, that leaves the card nothing, so it is left out altogether; beside Intel's too, where it embeds (it sees since kit 2.103.0, Qwen3-VL-2B). Beside AMD's, which doesn't embed, the card keeps embeddings: the first embedding request starts its server, and the keeper stops it after `gpuIdleStopMinutes` unused. An NPU whose embeddings failed at setup leaves them to the card the same way. A reranker stays off the card beside an NPU. The processor stays a candidate as before. Without an NPU, the switch means nothing. The rule is the core's `withoutGpuBesideNpu`; the node part reads the switch afresh for each request (`gpuWithNpu()` in manor.ts). Reeve follows the same rule for its own requests, and the keeper (the Smith, else Reeve) stops a card's llama-servers for the NPU's work while it's off, and its on-demand ones once unused; it never starts either. Setup follows the same rule (the core's `cardWorkBesideNpu`, which `withoutGpuBesideNpu` uses): with the switch off, a card beside an NPU is set up only for that work (NPU-VENDORS.md, What setup does).

## Model servers: busy, loading, and how long a request may take

As measured on GenieX v0.7.0 on the Snapdragon X2 Elite (2026-10-03): GenieX keeps one model loaded at a time and unloads it after 5 idle minutes (`--keepalive`); loading one takes 9 to 15 s (in every memory state tried, from 39 GB to 63 GB committed, with the model's files cached or read from disk), and a chat request after a vision one loads the chat model again. While it loads a model or answers a request, it answers nothing, not even `/v1/models`. npu-embed answers 503 while it loads.

- **A look at a server** is a GET of its `/v1/models`, waiting 3 s (`probeMs`): an answer is **ready**; a 503, or no answer from a server that took the connection, is **busy**; a refused connection (or any other answer) is **down**.
- **In its turn**, a request looks at its server afresh (a server can stop between turns: Reeve stops idle ones). Ready: on. Busy: it waits for ready, up to 180 s (`readyWaitMs`), and never starts a second server. Down: it starts the server from its `startCommand`, which has 30 s (`startWaitMs`) to take connections; a command that exits with nothing answering has failed at once. GenieX exits at once (code 0) when another server holds its port.
- **While the manor is stopped** (Manor's Settings, **Stop the manor**: `stopped.json` in Manor's folder, until **Start the manor**), a server that is down isn't started, from kit 2.99.1: `ensureServer` throws `ManorStopped` (a `ServerNotRunning`) instead, so nothing is marked failed and the request goes on to a server that is already running, if one serves it; with none, it says the manor is stopped. The keeper's restarts are refused the same way. manor.ts' `manorStopped()` reads it; under `node --test` only a test's own `MANOR_HOME` counts. The NPU benchmark starts its own servers (npu-server.ts' `startServer`) and isn't held: the owner stops the manor to run it on a quiet PC.
- **On the NPU**, each chat or vision turn starts with a **warm-up**: a one-token request to the turn's model, given 105 s (`requestBaseMs` + `coldLoadMs`). The request after it runs warm. A warm model answers the warm-up in about 0.15 s.
- **The warm-up is skipped** when the server was already up (not just started, nor found busy) and answered this same model within its keepalive, less 30 s: GenieX's `--keepalive` in the endpoint's `startCommand`, else its default, 300 s. Every agent writes `<accelerators>/<id>.served.json` (`{baseUrl, model, at}`) after each answer, so one agent's turn tells the next. Another model answered since, another server, or no record: the turn warms up.
- **A background chat or vision request** may take 15 s (`requestBaseMs`) plus 0.3 s for each token it may answer (`requestPerTokenMs`; GenieX writes about 34 a second), and never more than the config's `requestTimeoutMs`. A person waiting, and embeddings, get the config's `requestTimeoutMs`. Off the NPU (no warm-up), a request whose server was just started, or found busy, gets 90 s more (`coldLoadMs`).
- **A timeout while the model was loading** (the warm-up's, or one with the cold-load allowance) is the model being slow, not the server failing: the accelerator is not marked failed. The request goes to the next candidate, if any; else background work is deferred, and that agent leaves the accelerator alone for 5 minutes.
- **The keeper stops idle model servers** (the Smith, else Reeve: the kit's `keeper.ts`, with `rules.json`'s `keeper` timings), looking once a minute: the NPU's server (and its embedding server: llama-server, or Intel's second OpenVINO Model Server) when no one has held or waited on the NPU for 10 minutes, or, on a PC with under 20 GB of memory, its route's own minutes (5 for GenieX and OpenVINO Model Server, 10 for FastFlowLM; kit 2.71.0, [NPU-VENDORS.md](NPU-VENDORS.md#resting-when-unused-kit-2710)), `npuIdleStopMinutes` in its config overriding either, and a graphics card's or the processor's llama-servers (chat, vision, embeddings and a reranker) when no one has held or waited on that accelerator's lock for 10 minutes, or, on a PC with under 20 GB of memory, 5 for a card that shares the PC's memory (integrated graphics, under 2 GB of its own, whose models hold the PC's own memory; kit 2.78.25, [NPU-VENDORS.md](NPU-VENDORS.md#a-card-that-shares-the-pcs-memory-rests-the-same-way-kit-27825)), `gpuIdleStopMinutes` in its config overriding either (0 never stops them). Each accelerator's idle time counts only its own lock and line (kit 2.77.6): before, a let-go of any accelerator's lock counted for all of them, so Reeve indexing on a card kept the NPU's servers up, and the NPU a card's. A let-go leaves its time only on the folder every lock shares (a slot's folder is removed), so the keeper counts that folder's time for an accelerator only when it was held, waited on or taken since the keeper's last look: at most a minute late, never early. At its first look, no later than lock.staleMs after the accelerator's lock was last taken. A card's servers stop sooner when `games.json` says a game is using the card and nobody has used the card for 2 minutes: the game gets the card's memory back (a card's three servers hold some 10 to 14 GB of it). The next request starts a stopped server again. Reeve also restarts any of these servers that is running but hasn't answered for 3 minutes while nobody uses its accelerator, and GenieX alone when its working set reaches 9 GB while nobody uses the NPU. It does each holding every one of the accelerator's slots, so never in anyone's turn: one slot through the accelerator's line, as a background request that joins only an empty line (`maxAhead` 1), and, on a card with more slots, the other slot folders as plain locks (waiting 2 s for each), so no request starts on a server being stopped; when someone is in line, it waits for its next look. An idle stop whose turn isn't had at once (within 2 s) gives way: someone took the accelerator after the keeper looked, so it was used. GenieX holds on to some 340 MB of committed memory for each model it loads, until it exits, and the NPU's DSP fails (a subsystem restart, and GenieX exits) after about a dozen vision loads in one process: stopping it frees both. On a PC with under 20 GB of memory, with no `npuIdleStopMinutes` in its config, the NPU's own embedding server (Qualcomm's llama-server, Intel's second OpenVINO Model Server) also gives way to its chat, in a request's turn rather than the keeper's look: a chat or vision request on the NPU first stops it when the NPU hasn't answered an embedding for 30 s, and the next embedding starts it again (kit 2.77.5, [NPU-VENDORS.md](NPU-VENDORS.md#the-embedding-server-gives-way-to-chat-kit-2775)).
- **The keeper stops orphans, only its own**: a model server's process (llama-server, GenieX, OpenVINO Model Server, FastFlowLM, or a configured program) on the manor's ports (18181, 18191-18199, 18282 and every configured server's) that no configured server is, by its program and the address its command line serves (an older build, a server an earlier config named), once it has seen it for 5 minutes (`orphanGraceMs`; 0 never), and says so in its log with the program's path and command line, **but only when it is the manor's own** (kit 2.31.0, the core of the fix): its program is in the manor's servers folders (the tools home's and Reeve's `servers\`), or a record says the manor started that very process (`started.<pid>.json`, below: the same pid and program, started within a minute of the record). Never by its port alone: a person's own GenieX on its default 18181, another program's llama-server, or a process whose program Windows won't name (another account's, an elevated one) is left alone.
- **Manor's `gpuWithNpu`** (above): while it keeps the graphics cards out beside the NPU, the keeper stops a card's servers as soon as nobody uses the card, and never restarts them.
- **The keeper brings the NPU's command up to its kit's** (`npu-refresh.ts`): setup writes the NPU's entry once, so a later kit's command (a server argument, its cap, a plugin option) would reach only PCs set up after it. Once for each kit version, in the background of its look, the keeper compares what setup would write on this PC's NPU (the same ports, the embeddings as before unless they're offered: below) with the entry: its commands, their environments, its caps and quirks. Its slots, timeouts (measured on this PC, or a person's) and switch are the PC's and stay. When they differ, nothing has to be downloaded (else it's left for setup), and nobody has held, waited for or used the NPU for 2 minutes (its own lock and line, with a let-go dated as the keeper dates it above; since kit 2.82.3, the agents' work turns in the folder every lock shares no longer count, which kept the look waiting for hours on a PC with many staff), it takes the NPU's turn (background, an empty line only; it isn't taken from it as a dead holder's for 40 minutes, since a new command's first compile can take minutes), stops the NPU's servers and asks the new command the test question, and a test embedding when the NPU makes them. Before the test it waits until nothing takes the connection on each port the test will ask (`/v1/models`, any answer counting, a 404 too), asking every 0.5 s for up to 30 s; a port still answering then isn't tested, since the old server would answer for the new command, and the problem names what it said. Only when it answers properly, and the entry didn't change meanwhile, is it written, every other key kept; otherwise its servers are stopped, the old command starts again at the next request, and this kit doesn't try again, unless the test failed for its server (it refused the connection, exited while starting, or an old server still answered on its port: `serverFailed`). Then a look from an hour later tests it again, three tests in all for a kit; an answer that makes no sense stays final. Its log says which arguments changed, or why it kept the old command, and when it tests again. What the test's servers print goes to `<tools>\servers\logs\npu-refresh.log`, each test after a line naming its command (a server that passes goes on printing there until the keeper next stops it). What it found goes in `npu-refresh.json` beside config.json: `{ "kit": "<version>", "at": "<ISO time>", "did": "set-up" | "current" | "refreshed" | "failed" | "needs-setup" | "not-route" | "no-npu", "problems": [...], "tries": <n>, "retryAt": "<ISO time>", "embedOffer": {…} }`, `tries` and `retryAt` for a failed test only; setup writes `set-up` when it writes the NPU's entry. A record from a newer kit is never taken back. An entry pointed at another server than the route's is left alone. While someone uses the NPU nothing is written, and a later look tries again.
- **The NPU's own embeddings, offered** (kit 2.86.0): an NPU entry that makes no embeddings, on a route that has an embedding server (Qualcomm's llama-server on the Hexagon, Intel's second OpenVINO Model Server), is offered them by the same look when the PC has room for them beside its chat (`npuMemoryFit`, as setup decides) and their server and model are already on the PC: nothing is downloaded for them, and without them the rest of the look goes on as before. Such an entry is a PC set up before its route made embeddings (a Snapdragon set up before kit 2.63.0) or one whose setup failed to start them; their files are there when setup, the NPU check or a card's own server put them there (a card's llama-server serves the same Qwen3-Embedding-0.6B file). In the same turn, after the chat's test, the route's server's files are copied over the embedding server's as setup does (Qualcomm's `overlay`, GenieX's libraries), then a test embedding is asked. When it answers, the entry is written with them, and the NPU makes the PC's embeddings from then on: on a PC whose Manor keeps the graphics card out while the NPU serves (`gpuWithNpu` off), the card then makes none (`withoutGpuBesideNpu`), and the keeper stops its embedding server once unused, as it does the card's others. When the copy or the test fails, the chat's new command, if any, is written without them, their server is stopped (the chat that answered is left running), and the record's `embedOffer` (`{ "server": "llama.cpp b11125", "tries": <n>, "at", "problems" }`, kept in every later record until they're taken up) says so. A later kit offers them again, three kits in all, and then not until the route's embedding server is another.

## The NPU at full speed (kit 2.85.0)

The manor's gentle pace keeps the processor, the graphics cards, the disk and the network quiet. The NPU is the one part of the PC that's there for this work, so it is the exception: model work an agent has left after a round runs back to back on the NPU while the PC has room for it, instead of a round's few calls every hour or so.

Measured on the Snapdragon X2 Elite (the owner's laptop, GenieX with Qwen3-VL-2B, 2026-10-18), with note-sized requests (about 340 prompt tokens and 53 answer tokens each):
- **A round today**: 10 notes (a round's calls: Porter's, Pinder's and Shepherd's 10, Herald's 6, Reckoner's 3) took 11.5 s, the first 3.75 s with the server's cold start, then 0.86 s each. Then the NPU rests until the next round, and its server is stopped after 10 idle minutes.
- **The whole manor's use**: 29 to 116 requests a day over the week before, 2 to 7 minutes of the NPU's time (token-tally.ts' counts). Idle more than 99% of the day.
- **Back to back**: 60 notes through `npuBacklog` took 53 s, 0.89 s each, the NPU busy 98.5% of it (the requests' own time over the stretch's), its server staying up the whole stretch (1.6 GB working set, unchanged). GenieX's own side on the processor was about 4 cores while it answered back to back (212 s of processor time in 53 s, 22% of this 18-core PC), inside the manor's ceiling with the other servers (apart.ts). The warmest thermal zone went from 45 °C to 53 °C, and no zone held the processor back.

**The rule** (`node/npu-pace.ts`, `npuPace()` and `whyGentle()`): full speed for a kind of work (chat, vision, embeddings) when every one of these holds; else the rounds' own calls, as before:
- **Manor allows it**: Manor's settings.json `"npuPace"` is anything but `"gentle"` (full when absent). `MANOR_NPU_PACE` (`full` or `gentle`) says for a process; under node --test it's gentle unless that says.
- **An NPU takes this work first**: the first accelerator serving it, in the order requests try them (Manor's `gpuWithNpu` applied), is an NPU. Full speed is the NPU's alone: work that goes to a graphics card or the processor keeps the rounds' pace.
- **Plugged in**, and Windows' energy saver off. A PC with no battery is plugged in; one where Windows can't say isn't taken for it.
- **Cool**: no thermal zone holding the processor back (Windows' `Thermal Zone Information` passive limit under 100%). A PC with no zones to say counts as cool.
- **The NPU to itself**: no other program used an NPU over a second's look (Windows' `GPU Engine` counters, raw, two samples a second apart: a compute engine on a device with no 3D engine, at `otherUsePercent` (1%) or more), except the manor's own model servers (GenieX, llama-server, OpenVINO Model Server, FastFlowLM, npu-embed). Windows Studio Effects in a call, Live Captions or the person's own AI app on it keep the staff to their rounds' calls.
- **Memory**: no more than the manor's ceiling of it in use (85%).
- **The processor**: under 60% busy (pace.ts' LOAD.busy), the model server's own side included.

**The look** at the power, the heat and the NPU's users is one Windows PowerShell 5.1 script (about 1.8 s, a second of it waiting between the two samples), shared: `npu-room.json` in the accelerators folder (below) stands for every agent for a minute (`roomFreshMs`); the first agent that needs it after that looks again, holding `npu-room.look` (a folder) while it does, and the others take the last look meanwhile. A look that fails, or takes over `lookWaitMs` (20 s), says why, and the NPU stays at the rounds' pace. The memory and the processor are this moment's, in each agent.

**A backlog** (`npuBacklog(name, next, { work })`, `startNpuBacklog` to run it beside the round): `next()` does one item (one request, and keeping what it answered) and says whether there was one. Each item is a turn of its own in the NPU's line, so a person's request (the interactive lane) and the other agents' get theirs in between; the rule is looked at again before each one. It stops when nothing is left, when the rule says gentle, after `stretchMs` (15 minutes) at a time, at an NpuBusy (the line full, or no turn in time: the next round tries again) or another failure, and when the agent stops. One by a name at a time in an agent, a task in its work status (`model-backlog`), and, started with `startNpuBacklog`, outside the round, so the round ends and gives its place in the work line back while the NPU works through the rest. It starts and stops no server: the one that's up answers them all, and the keeper's idle stop and recycling wait for a gap, as for any turn.

**How busy each accelerator was** (token-tally.ts' `busyToday`): every agent's requests, embeddings included from kit 2.85.0, counted by accelerator and the PC's own day; the work status gives each accelerator's line its `today` ([WORK-STATUS.md](WORK-STATUS.md)).

## Games

A gaming desktop is for games first. While a game or another full-screen 3D program uses a graphics card, background work doesn't run on that card: it goes to another accelerator, or waits. A request someone is waiting on still may. A card counts as in use by a game while any other program's 3D engine on it is over 25% (Windows' `GPU Engine` counters, by the card's LUID), checked at most every 15 seconds. Heiward's ThreeDWatch does the same for its scans.

## A slow start

A PC can come up from a restart slower than usual and stay so until the next restart. An AMD Ryzen AI 7 350 that went into Modern Standby in its first two minutes (its lock screen turned the display off) decoded qwen3.5:2b on FastFlowLM at about 77% of its usual speed all day, while it read prompts as fast as ever, and a restart brought it back. Nothing but the speed shows it, so the kit keeps the speeds (kit 2.82.2, `boot-speed.ts`), and Manor's accelerator card says when this boot is slow.

- **Kept:** each chat answered through `npu.ts` whose server reports its decode speed (FastFlowLM's `usage.decoding_speed_tps`; OpenVINO Model Server, GenieX and llama.cpp's usage don't), by boot, accelerator, model and answer size. A server's decode speed counts its first token's wait too, so a short answer reads slower than a long one on the same boot, and answers are kept by size: 16 to 31 tokens, 32 to 63, and 64 and up (the core's `SPEED_SIZES`), each compared only with itself. Shorter answers, and vision's, aren't kept. A boot is when the PC started: the clock less Windows' uptime, which goes on through sleep and standby, so a restart starts another and waking doesn't; two boot times within 2 minutes are one.
- **Judged** (the core's `bootSpeed`), from every program's speeds together: for the model and size with the most answers this boot, among those with at least 8 this boot and 8 in an earlier boot, this boot's median against the usual, the fastest earlier boot's median, so an earlier slow boot doesn't lower it. This boot is slow at 85% of the usual or less (rules.json's `speed`). Until there's enough of both, nothing is said.
- **Said** (the core's `say.slowBoot`): "about 17 tokens a second since this PC started, against 23 after earlier starts; restarting the PC usually brings it back".

## Shared files

Every agent reads and writes these the same way, in `%USERPROFILE%\.npu-agent\accelerators\` (beside `locks\`, moved with it: with `NPU_AGENT_NPU_LOCK` set, the folder `accelerators` beside the lock folder's parent; a scratch `REEVE_HOME` gets its own). Each is written whole (a temporary file, then a rename), and anything unreadable counts as absent.

- `<id>.failed.json`: `{ "since": "<ISO time>", "reason": "<one line, at most 300 characters, starting with the kind of request: chat, vision or embed>", "by": "<who>" }`. The ISO time has its zone (`Z`, as every program writes it); a time without one counts as unreadable. The reason is the failure's first line, trimmed ("it failed" when there's none). Written when a request on the accelerator fails as above; the accelerator is skipped until 10 minutes after `since` (a marker exactly 10 minutes old has expired); a success on it deletes the file. A marker is about the accelerator's model server, so only programs that use the servers write or clear them.
- `hardware.json`: what this PC has (What this PC has, above). Written by setup and the keeper; read with every config.
- `started.<pid>.json`: `{ "pid": 4242, "program": "<the server's full path>", "base": "http://127.0.0.1:18183", "atMs": <when> }`, written by whoever starts a model server from its `startCommand` (kit 2.31.0), so the keeper knows the process for the manor's own. Records older than 30 days are dropped.
- `games.json`: `{ "checkedAt": "<ISO time>", "cards": { "<id>": { "busy": true, "percent": 87, "by": ["game.exe"] } } }`. Whoever finds it older than 15 seconds checks the counters again and rewrites it; everyone else reads it. A card missing from it isn't busy. `percent` is the busiest 3D engine's, rounded; `by` lists the programs (`name.exe`). Not counted: the checking process itself, `dwm.exe`, and the model servers (`llama-server.exe`, `geniex.exe`, and any configured `startCommand` program). A check that fails leaves the file as it was. A card's LUID in the counters is lowercase `0x<high>_0x<low>`. With no enabled graphics card in the config (no local AI set up, or none on a card), an agent asking whether a game is being played (the kit's `gameNow`, kit 2.87.0) checks the cards `hardware.json` lists instead, each by the id its name gives (`gpu-` and the name); with no `hardware.json`, there's no check.
- `npu-room.json` (kit 2.85.0): `{ "at": <ms>, "plugged": true | false | null, "saver": false, "batteryPercent": 80 | null, "passiveLimit": 100 | null, "npuUsers": [{ "pid": 4242, "name": "geniex", "percent": 89 }], "problem"?: "<why the look failed>" }`, the last look at the PC's room for the NPU at full speed (above). Whoever finds it a minute old looks again, holding the folder `npu-room.look` while it does (a folder over 20 s old is a look that died, and is taken back); everyone else reads it.
- `usage\<day>\<program>.json`: each program's requests by day, counts only (token-tally.ts): what the NPU benchmark's mix weighs, and each accelerator's day (`busyToday`). A day is the PC's own date from kit 2.85.0 (UTC's before), and each row names its accelerator (`acc`) from then.
- `speed\<program>.json` (kit 2.82.2): `{ "agent": "<program>", "boots": [{ "boot": "<ISO time>", "rows": [{ "acc": "npu", "model": "qwen3.5:2b", "size": 16, "tps": [20.51, 20.62] }] }] }`, the decode speeds one program's chat answers were written at (A slow start, above): the latest 30 a row, the latest 10 boots, oldest first. Speeds only, never what was asked or answered. Each program writes only its own; anyone may read them all.

## What each part does

- **The Smith**: keeps the accelerators and their servers (detects them, sets up their servers, offers them in Settings, and the keeping above), with the kit's `keeper.ts`, `setup.ts`, `detect.ts` and `accelerator-config.ts`. It uses no model.
- **Reeve**: routes its own chat, vision and embedding requests by the rules above, and starts servers when needed. Where there is no Smith it keeps the accelerators too, with the same kit code; where the Smith is installed it leaves the keeping to it, and its Settings page links to the Smith's.
- **The hires' kit** (`npu.ts` and its lock and line): the same choosing, per request; one lock and line per accelerator; the game check; the failure markers.
- **Heiward**: its AI already runs on the NPU, a chosen graphics card (DirectML) or the CPU. On a card, it takes that card's lock per batch, as it does the NPU's (the first slot only; the CPU it leaves unlocked). Auto is the NPU, then a graphics card it has checked (with its current driver), then the CPU. It records why it fell back, and `status --json` says which device and card. Heiward runs its models in its own process, not behind a server, so a failure of its tells nothing about a device's servers: it keeps its failure markers in its own folder (by the same rules, through the kit's dotnet part), and neither writes, reads nor clears the shared ones. It keeps its own game watch (ThreeDWatch, on the scan's card) rather than `games.json`.
- **The Auditor**: audits each accelerator. Each one's toolchain (its driver, its server and version, its models) has its own fingerprint and baseline.
- **Manor**: the page's NPU card becomes **Accelerators**, one per accelerator, each with who holds it (per slot), for how long, when it should let go, and its line.
