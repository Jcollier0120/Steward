# Steward

Looks after your repositories: claims versions, and builds and releases what you merge, where you say yes.

The *steward* ran the household for its lord: he kept the keys, saw that every servant had what the work needed, and carried the lord's orders to each of them. Its mark is a ring of keys.

One of the agents employed at Manor, the home of the local agents on this PC. Its page is http://steward.localhost:19494/.

It is a developer's hire, sold for the Steward's office, and it has two jobs:

- **On your PC: your own repositories** (below). Every PC.
- **On Castellan's own PC: Castellan's release machinery** (the kit, its rollout, and the Steward's own releases; from "The kit" on). Only on the laptop Castellan is made on, and there only where Settings' **Releases Castellan itself** (`releasesCastellan`) is on.

**Which PC this is** (`src/maker.ts`) is the maker's laptop itself: its firmware's (SMBIOS) UUID, as Windows keeps it (`HKLM\SYSTEM\HardwareConfig`, `LastConfig`), salted and hashed, the same check as Manor's customer view; the Steward holds only the hash. No file, setting or environment variable makes another PC the maker's (`STEWARD_CUSTOMER=1` only ever takes it away, to see the Steward as a customer has it). Everywhere else:

- **Releases Castellan itself** reads as off whatever settings.json says, and Settings don't offer it, so the kit, its rollout, the Steward's own releases and PRs and the releases repository are out of reach, and the page shows none of them.
- **Castellan's own repositories are its makers' alone.** One whose origin is under the maker's GitHub account (Manor, the site, the Exchequer, the releases repository, every agent), or that takes the id of one of Manor's agents (its shipped `staff.json`) or of the manor's own repositories (`manor`, `steward`, `kit`, `exchequer`, `castellansite`, `manor-releases`), is never offered or looked after, and **Look after**, `employ`, `claim-version`, `release-version` and a save in Settings each refuse it in a sentence.
- **Except a version claim from the maker's other development PCs** (Steward 0.36.27, `claimRefused` in `src/maker.ts`). A second laptop the maker develops on (it never merges, releases or deploys) claims and gives back versions of Castellan's own repositories, and of the kit from a Steward clone, wherever GitHub says the account `gh` is signed in as can push to that repository; a customer's can't, and nothing on the PC says otherwise. Its claim goes to the repository's claims ref (`refs/manor/claims`), which every PC reads, or nowhere: kept on that PC alone, no round would ever share it, so with GitHub out of reach `claim-version` says nothing was claimed. Nothing else of Castellan's moves there. To claim from such a PC: Developer options on (with no Manor there, `"developerOptions": true` in `%USERPROFILE%\.steward\settings.json`), a clone of the Steward with `npm ci` and `npm run kit` run in it, and, in the clone of the repository the work is on (where Reeve isn't installed to find it), `node <Steward clone>\src\cli.ts claim-version <repo> --branch <branch> --for "<what>"`. `vouch` there runs only for the Steward's own clone (it vouches for repositories in Settings, and Castellan's aren't): for the others, the build on the maker's laptop tests main's newest commit itself before it releases it. One already in settings.json is left there, unused, and Settings say why. A repository of yours whose name is an agent's gets its own id (`porter-2`).
- `claim-port`, `release-port`, `ports` and `mine`, and a claim of the kit's version, answer that they are for the people who make Castellan; the rounds raise no port alarms.
- **Developer options** (Manor's switch, or the Steward's own `"developerOptions"` without Manor): off, the Steward does nothing. Its rounds don't run, every stage and the commands that work on repositories answer with one plain line, its buttons and reads say the same (Manor's `/api/alarms` and `/api/version-queues` keep their shape, empty), its Settings form is left out, and its page is that line alone. On the maker's laptop the switch never holds it: the release machinery runs whatever it says.

## Your own repositories

Reeve lists the git repositories on this PC (his `GET /api/repos`, else the scan he keeps in `%USERPROFILE%\.reeve\repos.json`). The Steward's page offers, under **Found on this PC**, those on GitHub that the account gh is signed in as can push to (one `gh api graphql` query asks `viewerPermission` for all of them), and every one on another host or on this PC alone (one with no origin is `local/<folder>`), less those it already looks after and those Reeve leaves alone (`src/found.ts`; the look is kept in `repos-found.json`, made again at most every hour, or with **Look again**). Nothing is looked after until you pick it. **Add a clone by its folder**, below the list, takes any clone Reeve didn't list, on any host or none.

**Look after** adds one to Settings, under **Repositories**, with what its clone says at its branch's tip: how to test it (`npm run typecheck` and `npm test` when package.json has those scripts, `cargo test`, `python -m pytest` with a pyproject.toml, `go test ./...`, `dotnet test` on its unit tests), the files that carry its version (package.json, package-lock.json, a `src/*.ts` with the same `version: 'x.y.z'` or `VERSION = 'x.y.z'`, Cargo.toml's or pyproject.toml's own, each .csproj at its top or a folder down that sets its own `<VersionPrefix>`, else a Directory.Build.props that sets it), no kit, nothing installed. One tick beside it, off unless you tick it:

- **Release each new version** (`release`): when its branch carries a version with no GitHub release yet, the next build releases it (The build pipeline, below: its newest commit tested first, unless a vouch covers it): with its own `npm run release` when package.json has a release script, else `tag`, a GitHub release `v<version>` of the branch's commit that the Steward makes itself (`gh release create`), its notes the version's entry in CHANGELOG.md, or GitHub's from the commits. A release command of the repository's own must make that GitHub release in the repository itself: one that finishes without it is a failed release, which the rounds then leave to you at that commit. Empty, it is never released.

**Its own pipeline** (Steward 0.36.266, `src/repoconfig.ts`). How each repository is built, tested, versioned and released is its own to say: a `.steward.json` committed at its top, or Settings' **Pipelines**, gives its build commands, its tests, how it is versioned (claimed up front, set by hand, by its tags, or never), its tag format, its notes, where a release goes (its host, a tag, a folder, its own command), how its own PRs merge, and whether it is vouched for and shares its refs with your other PCs. A repository with neither is built and released exactly as before. One whose pipeline can't be read is held, each mistake said, and the others carry on. `steward build --dry-run <repo>` prints each step a build would take, running nothing, for one looked after or any clone. [docs/PIPELINE.md](docs/PIPELINE.md) has each option, each host's sign-in, an example for each stack and a dry run; [samples/pipelines](samples/pipelines) has hello, world on each (`node tools/samples.ts` spins them up).

Two more for each repository, in Settings: **Refresh after releases** (`refresh`), a command run after any stage that released something, whosever release it was (a site's `npm run sync`, which writes every product's release notes and newest downloads into a file the site is built from). It runs in a fresh worktree of the repository's branch on origin, `<id>-refresh` in the work folder, with its packages and gh at hand. When it changed tracked files, the repository's tests run there, and only when every one passes is the change committed ("Release notes and downloads after <what was released>") and pushed to the branch, never forced. Nothing changed: nothing pushed. A failure pushes nothing, is kept in `refresh-failed.json` and is an alarm until a refresh of that repository goes through; the next release tries again (`src/stages/refresh.ts`). And **Note** (`note`), a word shown first on its row of the page: why it isn't released yet, say.

**You merge, it builds.** The Steward merges no one's pull requests. Whoever writes one pushes it, runs `steward vouch` in the clone it was pushed from (The rollout, "Merging and vouching", below), and once GitHub says it merges cleanly, merges it: `gh pr merge <n> --repo <owner/name> --merge`. At each build the Steward takes the newest commit on each repository's branch, and when it carries a version not released yet, tests it once and releases it. Settings' **Merges PRs** (`merges`) is no longer used, and hidden.

**Builds and releases by itself** (`byItself`) is off on a new install too: until you switch it on, nothing is released but by a button. **Versions claimed up front** (below) work for any repository: one in Settings, one Reeve found here, or the clone the command runs in. Every release goes to the repository's own host (or where its pipeline says: a tag, a folder, its own command), never anywhere else: the Steward passes `MANOR_RELEASES_REPO` empty to every release command it runs.

What it never does on your PC: roll a kit out, release itself, hand work to the Wright (only where the Wright is installed), or read the Surveyor's page where the Surveyor isn't installed. Settings show only what applies.

**Tending and the manor-wide alarms belong to Manor.** Keeping the staff's pages up (`src/tend.ts`) and the alarms about the manor as a whole (Manor's page and updates, the ports, the Surveyor's problems, Reeve's alerts, an agent down) are the household's, not a developer's, so every PC should have them whatever agents it holds: they go to Manor, which every PC has. Until a Manor does them, the Steward does, as before. A Manor that does says so in its `GET /api/state` as `"keeps": ["tend", "alarms"]`; from then on the Steward leaves both to it and raises only the alarms of the repositories it looks after.

### One core, two drivers

All the shared decision logic is the **core**: the ticket order and the late, dead and aged rules, a lock holder's eviction, the turn and the plain lock as a state machine, reading, checking and auto-ordering Reeve's accelerator config, the candidates and the pick, failure-marker expiry, games-busy, the id slug, a request's size, and the messages. It reads no file and has no clock or randomness of its own, so it gives the same answer in any engine: a driver hands it what it read and the time, and does what it says.

- **The turn** is `startTurn(rules, options)`, then `step(state, observation)` until it ends: each step is the actions to take in order (`mkdirs`, `write`, `touch`, `list`, `alive`, `remove`, `mkdir`, `read`, `stat`, `rmdir`, `note`, with paths as names below the locks folder), how long to wait after them, and, once it has, how it ended (`held`, `timeout`, `full`, `io`). The driver performs them, waits, and calls `step` with the clock and each action's result. `release(state, now)` lets go the same way. A state is plain data.
- **The timings and limits** are data, `spec\rules.json`, which a driver reads once and passes to the core (`checkRules`).
- **The node part** carries it out with Node's fs and timers, and stays async, so a turn never blocks an agent's server. Its modules keep 1.0.0's boundaries and exports, so the hires' imports didn't change.
- **The dotnet part** carries it out with .NET and Win32 I/O, running the core's JavaScript in [Jint](https://github.com/sebastienros/jint) (4.16.4, pinned in `Steward.Kit.props`), a JavaScript interpreter written in C#: no native code, so it runs on x64 and Arm64, in a Store package and in a self-contained or single-file exe, trimmed too. The core's modules and rules.json are embedded in the assembly, and values cross as JSON text, with no reflection. `KitCore.Shared` hosts it (thread-safe); `AcceleratorLock.Acquire` takes a turn, blocking or async; `FailureMarkers` reads, writes and clears markers in any folder.
- **The vectors** in `spec\` run against the core directly and through each driver: here, `kit\test\vectors.test.ts` (the core, the node part) and `kit\test\dotnet` (the core in Jint, the dotnet part). Reeve's npu-embed/npu_lock.py, a Python implementation of the lock, runs npu-queue-vectors.json.

A logic change is one edit to the core; only a new kind of action touches the drivers. WebAssembly was considered and rejected: it needs another toolchain and a native runtime in C#, and gains nothing over JavaScript, which the TypeScript agents already run.

### The agent interface

What the kit needs from the agent it sits in, kept small:

- **`src/app.ts`** exports `APP` (`id`, `name`, `role`, `version`), `appRoot`, `devCheckout`, `dataDir`, `port`, `pageUrl` and `HOST_NAME`. The kit imports it as `../app.ts`.
- **`src/settings.ts`** exports `SETTINGS_SPEC`, the agent's settings for the kit's Settings panel. Only agent-checks.ts imports it (as `../settings.ts`); the agent hands it to `serve()` itself.
- **`src/cli.ts`** is the entry point: install's sign-in task runs `src\cli.ts open`, and `serve` runs the page.
- **`art/icon.svg`**, which the page serves as `/favicon.svg` and Manor shows.
- **`package.json`**: its `name` is `APP.id` and its `version` is `APP.version` (release.ts checks it); and **`kit.json`**.
- **Its own routes** (`serve()`'s `get` and `post`) leave the kit's alone, `KIT_ROUTES` in kit-routes.ts: `serve()` refuses one named as the kit's, so the kit's `POST /api/stop` always ends the page.

`agent-checks.ts` checks all of it: each agent's `test/agent.test.ts` is one line, `import '../src/kit/agent-checks.ts';`, and fails when the agent and the kit disagree (its schema and defaults too, as each hire's settings-kit.test.ts used to check).

### With Manor: manor.ts

An agent works at a manor when Manor is installed here: its folder (`MANOR_HOME`, else `%USERPROFILE%\.manor`) has `settings.json` and `app`. `manorLink()` reads that settings.json afresh each time, as Manor does, and is null without Manor. It gives:

- **Manor's name, port and page**, for the title bar's "Back to <manor>", with Manor's icon served from the agent's own address as `/manor-icon.svg` (`manorIcon()`).
- **The manor's theme**, which page.ts stamps on `<html data-theme>`; the agent's Theme menu then says it's Manor's, with a link to change it there.
- **Its Developer options** (kit 2.5.0): `"developerOptions"`, the switch on Manor's Settings page that holds or vacates the developer roles, or null when Manor hasn't said. An agent with developer features of its own asks `developerOptions(ownSwitch)` on each page load and each round: `{ on, setBy }`, where Manor's value wins when it says (`setBy` is Manor), else the agent's own switch. While `setBy` is set, the agent shows page.ts's `developerOptionsNote(setBy)` in place of its own switch: "<manor>'s Developer options set this", with "Change it in <manor>" to Manor's Settings (`manorSettingsUrl()`, its page at `#/settings`). Without Manor, or before Manor says, its own switch works as ever. No hire has developer options yet; Heiward, whose page isn't the kit's, follows the same key itself.

**Non-employee projects** (kit 2.18.0): `manorProjects()` gives the repositories this PC's manor looks after without employing them: Manor's settings.json `"projects"` (its Settings page's Non-employee projects), checked, or none without Manor. Each is `{ name, checkout, repo, branch, test, versionFiles, cleanBranches }`: `repo` owner/name or null, `branch` "main" unless said, `test` a command run in the checkout or null, `versionFiles` the files the Wright sets the version in (empty: the manor never changes its version), `cleanBranches` whether Reeve deletes branches already merged into `branch` (true unless said). An agent that cleans up and fixes repositories works on them as well as on the staff, and never as staff: no kit, no Steward, no merge or release. The rules are `projectsFrom(raw, own, problems)`, which Manor's own settings use too, so the two agree: an entry whose repository or clone's origin is the manor's own, or whose checkout is, is inside or holds one of the Steward's employees' checkouts (`manorOwn()`), is left out.

### What the ping says

Every kit agent's `GET /api/ping` answers what Manor needs to show it without starting anything: `app`, `name`, `version`, `pid`, `running` (on duty), and from kit 2.9.0 `stoppedSince` (when it went off duty, null while on) and `summary` ("On duty.", or "Off duty since 2 hours ago: its scheduled rounds are paused."), the same words as `status --json`; then its rounds (`lastRunAt`, `lastRunOk`, `nextRunAt`, `runningSince`, `rounds`) and the agent's own fields. So Manor runs an agent's status command only when its page doesn't answer.

### What the agent is working on

From kit 2.76.0, every kit agent's `GET /api/peer/work` answers its **work status** ([kit/spec/WORK-STATUS.md](kit/spec/WORK-STATUS.md)): what it may run at once, what it runs and what waits, in which of the PC's lines (the checks pace's turns, the work line, the first-round line, each accelerator's), its recent results by code tree, and what holds its work up. Manor's Work page gathers it from each agent on the PC, and over Manor's link from the licence's other PCs. The Steward adds its stages (Stages at once). No PR waits for it, so it names nothing that holds a repository's work up.

### What the kit leaves in the data folder: round.json

Each round an agent runs with schedule.ts's `every()` leaves its outcome in `round.json` in the agent's data folder (kit 2.8.0), the same in every agent, so the Surveyor reads one file per agent: `{ "rounds": { "<name>": { "started", "finished", "ok", "error", "everyMs", "next" } } }`, one entry per schedule by its `name` ("round" unless said). [spec/ROUND.md](kit/spec/ROUND.md) says the shape and when it is written. A round.json that can't be written never fails the round. The node part only, for now: the dotnet part has no scheduler.

### kit.json, and filling src\kit

Each agent pins one exact kit version and its parts in `kit.json`:

```json
{
  "kit": "2.0.0",
  "parts": ["node", "web", "spec"]
}
```

**A part brings the parts it needs**, whatever kit.json names: `node` brings `core`, `core` brings `spec` (its rules.json), `dotnet` brings `core`. So a hire's pin names the three it always did, and gets four. A kit from before 2.0.0 has no core, and then none is filled. `src\kit\PARTS` still says the parts kit.json pins, and tools/kit.ts's line says what it filled.

Its `src\kit\` is git-ignored and filled by `tools/kit.ts`, the one shared file left in each repository: small, dependency-free, the same in every agent. This repository's `tools/kit.ts` is the canonical one, and `bump` hands it out with each new pin (below), so a change to it reaches every agent as a kit change does. `npm run kit` runs it, and so does every npm script that runs the kit: `pretest`, `pretypecheck`, `prestart`, `prestop`, `prestatus` and `preopen`, and `serve` and `release` before their command. So a fresh clone works whichever it runs first. It writes `src\kit\VERSION` (and `PARTS`), and does nothing when they already match the pin. Otherwise it takes the pinned version from the first of:

1. `--from <dir>`, or the `STEWARD_KIT` environment variable: a kit tree on this PC, such as a Steward checkout's `kit\`, copied every time. For development; it warns when the tree's version isn't the pinned one, and a release refuses that.
2. A sibling checkout, `..\Steward\kit`, when its VERSION is the pinned one: with the default checkouts, `C:\Projects\<Name>`, that is `C:\Projects\Steward\kit`.
3. `%USERPROFILE%\.steward\kits\<version>`, the cache.
4. The kit release: `https://github.com/Jcollier0120/Steward/releases/download/kit-v<version>/kit-<version>.zip` and its `SHA256SUMS.txt`, over plain HTTPS with no sign-in (the repository is public), or through `gh release download` if that fails. The zip is checked against SHA256SUMS.txt, unpacked with Windows' own tar.exe, and kept in the cache.

An agent's release (`src/kit/release.ts`, `npm run release`) carries `src\kit\`, with `kit.json` and `tools/kit.ts`, and its release.json says `"kit": "2.0.0"`. It refuses to build when `src\kit\VERSION` isn't the pinned version. So an installed agent needs neither the Steward nor GitHub. An agent that announces itself to every Manor (Manor's "New agents, announced on GitHub") keeps `manor-agent.json` at its root: the release copies it beside the zip, lists it in SHA256SUMS.txt and publishes it with the zip, and refuses to build when its `agent.id` isn't the agent's, its `release.repo` isn't origin's, or it isn't otherwise one Manor would take (a Node release, installed in `%USERPROFILE%\.<id>\app`).

**A fresh clone of a hire builds** with `npm install`, `npm run kit` and `npm test`. `npm run kit` needs one of the sources above: the kit release on GitHub (no sign-in once this repository is public; `gh`, signed in, while it's private), or a Steward checkout beside the hire.

### How the kit was found

`tools/kit-from.ts` compares the hires' trees (CRLF made LF) and, with `--write`, lays the shared files out as the kit, their imports rewritten for their new places. Kit 1.0.0 was seeded from the eight hires' `release-0.3.1` branches, each checked out on its own: the commit "The kit, seeded from the eight hires' common files" is its output, the hires' code only moved (into `kit\src`, before the kit had parts), and the next commit holds 1.0.0's changes. Run today, with Manor's newer settings kit as an overlay, it writes the parts layout (each `<…>` a checkout's folder):

```powershell
node tools/kit-from.ts --from <Porter>,<Auditor>,<Clerk>,<Herald>,<Warrener>,<Aletaster>,<Miller>,<Pinder> `
  --overlay "src/settings-kit.ts=<Manor>\src\settings-kit.ts,src/settings-panel.js=<Manor>\web\settings-panel.js" --write
```

`node tools/kit-from.ts --from <dirs>` without `--write` only reports: after 1.0.0 the kit changes in `kit\`, and a re-run with `--write` would put the hires' old copies back.

## Kit releases

A kit version is released once, as **`kit-v<version>`** in this repository, with `kit-<version>.zip` (VERSION, CHANGELOG.md and the parts, `core\` and `dotnet\` too, from `kit\` at HEAD through `git archive`, never the tests) and `SHA256SUMS.txt`. Its notes are the changelog's entry. `npm run kit-release` builds them into `artifacts\kit\`; `npm run kit-release -- --publish` makes the release, from a committed and pushed tree, and refuses a version already released.

The Steward's own releases stay **`v<version>`** (`npm run release`), and are separate: a kit release needs no Steward release, and a kit release is never marked Latest. On duty, a build makes both itself when main carries a version that has none, the kit once it passed its trial on every agent (Page and commands, "Its own releases"). What changed in each Steward version is in [CHANGELOG.md](CHANGELOG.md).

## Making a kit change

1. Edit `kit\` (and its tests in `kit\test\`), or `tools/kit.ts`, raise `kit\VERSION`, add its entry to `kit\CHANGELOG.md`, and set this repository's own `kit.json` to the new version (a test checks they agree). `npm test` runs the kit's tests on the fixture, tools/kit.ts's, and the vectors against the core and the node part; then the dotnet part's, when a .NET 10 SDK is found (`npm run test:dotnet` runs those alone, and fails without one).
   - **A rule** is a change to `kit\core\`. `npm run core-types` then writes its `.d.ts` again (a test says when they're stale), and `npm run vectors` writes turn-vectors.json and accelerator-vectors.json from the scenarios in `kit\test\*-scenarios.ts`: their diff is the change in behaviour, for review. A timing or a limit is a change to `kit\spec\rules.json`.
   - **The dotnet part**: `npm run test:dotnet-publish` publishes it as Heiward does (self-contained, single-file or not, Arm64 and x64) and trimmed, and runs each exe. Jint's version is pinned in `kit\dotnet\Steward.Kit.props`.
2. To try it in an agent before releasing it: `node tools/kit.ts --from ..\Steward\kit` there, or `steward bump --kit-from kit` (below).
3. PR it to the Steward, with the Steward's own version raised too, vouch for it and merge it yourself (The rollout, "Merging and vouching", below): the Steward merges no one's PRs. Once main carries a kit with no `kit-v<version>` release, the kit is tried on every agent before it is released (`src/stages/trial.ts`): each agent's main bumped to it as the rollout will bump it, in a worktree of its own, its kit filled from main's `kit\` and `tools/kit.ts`, nothing committed or pushed, and its checks run. The trial goes a few agents at a time, at most 8 minutes each round, between builds too, so a build finds its kit tried. A build waits for a trial still going until its time runs out; then the kit waits for the next build, and its trial goes on from where it was. An agent none of whose kit files change from the kit it pins isn't tried at all, and one whose files change runs only the tests those files reach; its rollout bump runs the same ones. An agent that fails with the new kit is checked once more as it is, without it: failing the very same way there, the failure is the agent's or the PC's, not the kit's, and doesn't hold the kit. One whose failure looks like this PC's load (a test killed, `EBUSY`), or that fails without the kit too but otherwise, is tried once more, alone, once the rest of the trial is done, and holds the kit only if it fails then too. A trial is kept by main's commit (`kit-trials.json`) and by the kit each agent gets (the kit's parts and `tools/kit.ts`), so main moving on with the same kit but for versions and changelogs keeps its verdict. Every agent passing, the build releases the kit and rolls it out, and an agent's rollout bump from the commit its trial passed at isn't checked a second time. One agent failing holds the kit alone, and the Steward's version that carries it, with one alarm that names each agent and the tests that failed: every other repository releases as usual. Fix the kit on main (a new kit is tried afresh), or the agent on its own main, so it passes with the kit and without it: an agent whose main moved since its trial failed is tried again.
4. Release it: `npm run kit-release -- --publish`, then the Steward's own `npm run release -- --publish`. On duty, a build does both by itself once the change is on main and its trial passed (below, "Its own releases").
5. Roll it out, a stage at a time: `bump`, `push`, `release`. On duty, the build that released the kit does that by itself too, and merges each kit PR itself (below, "The rollout in a round").

## The rollout

Each stage is a command and a button on the page (each asks first, and only the ticked employees are touched). Each reports for every employee (done, skipped, refused or failed, and why), and the page shows the last stage's results and log. Stages run side by side on this PC, as many at once as Settings' "Stages at once" (`stagesAtOnce`, 2) allows, the page's and a terminal's counted together (slots in the data folder's `locks`: `stage`, `stage.2` …). Each works on a repository only while it holds that repository's lock (`locks\repo-<id>`, `src/stages/slots.ts`), so two stages never touch one repository at once: a Release pressed while a round runs releases its repositories straight away, and where both want the same one, the second waits for the first to finish with it, with a line in its log saying so. One round runs at a time. With every slot taken, a button is refused until one ends; set it to 1 for one stage at a time, as before. On duty it also does them by itself, at a build: it bumps and pushes a new kit to each employee behind it, merges each kit PR itself, and the build releases it (Page and commands, below).

1. **`steward bump [--kit <version>] [--employees a,b]`**: for each employee that takes the kit, a fresh git worktree of its branch on origin (fetched first), on the branch `steward/kit-<version>`, in the work folder (`%USERPROFILE%\.steward\work\<id>`). Never the person's own checkout. There `kit.json`'s pin moves to the kit, `tools/kit.ts` becomes the Steward's when it differs (for an agent whose kit is filled by it), and its changelog entry is written in `changes/steward-kit-<version, dots as dashes>.md`, with `changes/README.md` added where it's missing, which puts the employee on the build pipeline (Steward 0.36.248, The build pipeline, below): no version is claimed or set, and the build's stamp gives it the next release's. Only an employee worked with plain git, which has no PR to stamp through, is bumped the old way: its patch version claimed and raised in every version file (package.json, both of package-lock.json's own entries, and src/app.ts, which release.ts requires to agree), and its entry put at the top of CHANGELOG.md. Then, for a Node agent, its packages: the worktree's `node_modules` is a junction to the set installed once for its lockfile in the work folder's `_modules` (`src/stages/modules.ts`: keyed by the lockfile's packages, its own name and version aside, so the hires share one set; `npm ci` runs there once per set, with the project's own scripts left out; the six sets most lately used are kept), or `npm ci` in the worktree if that can't be done. Removing a worktree removes the link, never the packages. Its kit is filled with the new tools/kit.ts, and its checks run (`npx tsc -p . --noEmit` and `npm test` for a hire). When every one passes, the changes are committed: "Porter: the Steward's kit 1.0.1" ("Porter 0.4.1: the Steward's kit 1.0.1" the old way). The Steward's tools/kit.ts is its checkout's, or, installed, the one its release carries. Checks that fail are run once more, as main's are at a build (a round bumps several employees at once, and a test that keeps time can fail under that load): a pass the second time is committed, and says so ("checks passed on a second try (the first: …)"). Failing twice leaves the worktree for a look, with the failed step's whole output beside it (`work\<id>.log`), and the failure names the tests that failed and their errors, read from `node --test`'s output (`npm test failed (exit 1): "its name" (its error), twice`), so the alarm says what broke. `--kit` defaults to the newest kit release; one that isn't released is refused, since the employees couldn't fetch it, unless `--kit-from <kit folder>` fills from a kit tree instead (for a trial). `--base <ref>` starts from a local ref instead of origin's branch. A bump made before and not pushed is made again from scratch; one already on origin is refused until its PR is merged or closed. A bump a person asks for (the button, or the command) also lets the rounds try again an employee whose rollout failed in a round (below).
2. **`steward push`**: each prepared branch is pushed (a plain push, never forced) and gets a PR against the employee's branch, titled "Porter: the Steward's kit 1.0.1" (with the version it set, the old way), its body the changelog's entries since the kit it had. A PR already open is left as it is. A person's Push leaves the PR open: the next build's rollout merges it, or merge it yourself. The rollout's own push merges each PR at once (Merging and vouching, below). Like Bump, a person's Push lets the rounds try a failed rollout again.
3. **`steward release`**: for each employee whose branch on origin pins the kit and carries a version with no GitHub release yet, a worktree at that very commit, and its release command run there (`npm run release -- --publish` for a hire), after `npm ci` for a Node agent whose release builds something: Reeve's builds its dashboard with vite. A hire's release (`npm run release`, whose scripts run only `node tools/kit.ts` and `node src/kit/release.ts`) packs its files with Node alone, so it gets no `npm ci` (`releaseNeedsPackages`, read from the employee's package.json; a release command it can't read gets `npm ci`, as every release did before). Releases happen a few employees at a time (Settings' `parallel`). Releases come from the branch, never from a PR's, so a release and its branch never drift apart. A version below one already released isn't released ("v0.4.20 on its branch is below v0.4.22, released already: a version above it (claim-version) releases what is merged"). At a build, that very commit is tested first, unless a vouch covers it (The build pipeline, below); the button's Release doesn't test it. Where main carries entries in `changes/`, a person's Release stamps them first, as a build does (0.36.248), and releases the version stamped. From kit 2.30.0 the kit's release publishes the same files to the Exchequer, Castellan's release service, as well (kit/spec/RELEASES.md, "Sold"): a release that reached GitHub but not the Exchequer is this Steward's release all the same (no "another Steward" alarm), and the Steward finishes it there itself (src/stages/exchequer.ts, 0.36.138): the agent's own `npm run release -- --exchequer`, in a worktree of the commit released, publishes GitHub's files of it. One the network or the Exchequer's own failing kept out is done, and every round tries it again once due (15 minutes, then further apart, up to three hours), with an alarm only after Settings' waiting hours; one the Exchequer refused (it doesn't sell the agent, or turned the draft down) raises an alarm at once, and a person's Release tries it again. Both alarms carry a **Publish it now** button (`askAgain`, through `/api/alarms/act`) that has a round try at once. The Steward's own release gets the same (0.36.139): `releaseStep` in src/stages/self.ts notes it pending under the Steward's id, and the rounds finish it with the Steward's own `npm run release -- --exchequer`. A newer release that reaches the Exchequer lets an older one waiting go.

   **The Assayer checks it first** (`src/tasting.ts`; Settings' `tasteBeforeRelease`, on by default; the retired Aletaster made this check until 0.36.154). Every release (a build's, the button's) waits, once its commit and version are known and before its worktree is made, for a passing release check of that very commit: its version files agree with the version, which isn't released yet and is the next step, every PR merged since the latest release has its changelog line there, and an agent of the house would be released under its own name (Assayer 0.4.22's `POST /api/taste`). The Steward reads the Assayer's token from its page (`GET http://127.0.0.1:20909/`, `<meta name="page-token">`), asks `POST /api/taste` with `{repo, commit, version, name, versionFiles, checkout}` (the token in `x-token`, no Origin), and, while the answer says `"state": "running"`, asks `GET /api/taste?id=…` every two seconds for up to 90 seconds. It publishes only when the answer says `"state": "done"` and `"release": true` (a pass, or a warning), and says so: "released v0.4.13 …; checked by the Assayer: pass". Anything else holds the release, with the check's reason ("v0.4.13 at 4c1d2e9 waits for the Assayer's release check: fail: …") and a link to it, and the next round looks at that employee again, whatever GitHub says. The holds are kept in `tasting-held.json`; one that lasts is an alarm (below). The gate never stalls the manor:
   - **No Assayer here** (`%USERPROFILE%\.assayer\app` absent, or `ASSAYER_HOME`'s), or **off duty for Developer options** (Manor's `developerOptions` false, and the Assayer a developer role in Manor's staff.json, or its own switch off, as its `/api/ping` says): released with "released without a release check: the Assayer isn't here".
   - **An Assayer that predates the check** (`POST /api/taste` answers the route's own 404, with no `verdict`, as against the 404 for a check it doesn't know, which has one and holds), or **whose page doesn't answer at all** (no connection, at any step): released, with a note saying which.
   - **The Assayer's own release** is never held by its check, so a broken Assayer can always be fixed.
4. **`steward staff [--json] [--no-fetch]`**, and the page's table: each employee's checkout and its branch, the version and kit on its branch (and whether its tools/kit.ts is the Steward's), its latest release and the kit that release carries, the open PRs of the Steward and the team (checks, mergeable, and whose), a bump prepared here, and the kit version the Steward hands out (the newest kit release, and this checkout's `kit\VERSION`).

(`status --json` is Manor's command, as every agent's is: the employees' status is `staff`.)

### Merging and vouching

The Steward merges no one's pull requests (0.36.124): it has no merge stage, catches no PR up and keeps no version queue. What it opens itself it merges itself, at once, at the head it pushed, its branch deleted (`mergeOwn`, `src/stages/mainbuild.ts`): a rollout's kit PRs, whose checks ran in the bump, and a build's stamp PRs, which change only versions and changelogs. One GitHub won't merge at once stays open: the next build's rollout merges a kit PR it finds open at the kit it rolls out; or merge it yourself, or close it. Every other PR is its author's to merge:

1. Claim its version first (Versions claimed up front, below), or write its entry in `changes/` where the repository keeps them there (The build pipeline, below). Push the branch and open the PR.
2. Run **`steward vouch`** in the clone it was pushed from (`node %USERPROFILE%\.steward\app\src\cli.ts vouch`, or `vouch <number>`). It runs the repository's checks as Settings give them at the clone's HEAD, which must be the PR's head with nothing uncommitted, and once they pass sets a commit status on that commit (`steward/tested`, success); a failure sets none. A branch with no PR yet is vouched for as pushed, once a version is claimed for it. Before any check runs, HEAD's version files (Settings' `versionFiles`, two or more) must agree, as a kit's trial needs them to (0.36.153): if they don't, it refuses in the trial's words and says what to set where ("the version files disagree: package.json 0.18.33, package-lock.json 0.18.33, src/mcp.ts 0.18.31; set 0.18.33 in src/mcp.ts"), the version claimed for the branch or else the highest of them, and runs and records nothing. A version below main's, or below the one claimed for the branch, is a warning. A PR of the Steward's own that changes what the agents take from the kit (its parts or `tools/kit.ts`, against where the branch left main) then has that kit tried on the agents too (0.36.240, `vouchTrial`): each agent main's trial would try, as that trial tries them (`kitTrialOfClone` in `src/stages/trial.ts`: a worktree of its own, only the tests the kit reaches, a scratch profile, nothing committed or pushed), one at a time, so the PC you're working at isn't loaded with more. An agent whose tests the kit breaks fails the vouch, named with the tests that failed ("kit 2.137.3 fails 1 agent's checks (Reeve), as main's trial would: Reeve: npm test failed …"): fix the kit, or the agent's tests on its own main so they pass with the kit and without it, and vouch again. One that fails without the kit too isn't held against it; one that fails as under load is tried once more, alone, after the rest; a try the network cut short fails the vouch, to be run again. A PR that leaves the kit as main has it (its changelog, its own tests or `kit/VERSION` alone) has no trial.
3. Once GitHub says it merges cleanly, merge it yourself: `gh pr merge <n> --repo <owner/name> --merge`. The vouch says so ("merge it yourself now, once GitHub says it merges cleanly (gh pr merge 17 --repo octocat/porter --merge): the Steward merges no one's PRs, and the next build releases main").
4. The next build releases it.

Where `npm test` is a plain `node --test`, a vouch runs only the test files the change reaches (`src/affected.ts`: through imports, the files that name what changed, and the code that reads a Markdown file where it lies; a version step or a changelog entry reaches none), and the status says so ("npm test (affected: 12 of 126 test files)"); what it can't follow runs the whole suite. Settings' `affectedTests` (on) switches it off. When the Assayer already passed every check on exactly HEAD's tree, or the whole checks passed on that tree here or on another PC (Code that already passed isn't tested again, below), nothing runs again. Checks that run five minutes past the vouch's usual time are stopped, and nothing is set.

A build trusts the vouch only when one of Settings' team accounts set it (GitHub's record of who did), on main's newest commit itself, or on the PR head a merge commit brought in unchanged (a PR merged while up to date with main): that commit isn't tested again before its release. Anything else on main is tested there first. The status isn't a check GitHub runs, so it never makes a PR's checks "passing" on its own.

## Converting a hire

Every hire has been converted, so the Steward itself no longer looks for the old kit's files; what converted them is kept in `tools/` (`tools/lib/convert.ts`, `tools/lib/relocate.ts`, `tools/lib/compare.ts` and the old kit's paths in `tools/lib/oldkit.ts`), and never ships. `tools/convert.ts <worktree> --version <new>` turns a hire that carries its own copy of the kit into one that takes the Steward's: it removes the 22 old kit files (`git rm`), rewrites the hire's imports to `./kit/…`, ignores `src/kit/`, adds `kit.json`, `tools/kit.ts` and `test/agent.test.ts`, makes npm fill the kit first, raises the version, and points the README at the Steward with a section on the kit. It stages; it commits nothing. It refuses any agent that isn't one of the eight hires, before it removes anything.

The eight hires were converted that way, each on a branch **`steward/use-kit-1.0.0`** from its `release-0.3.1`, each in a worktree of its own, at version 0.4.0, then filled from this checkout's kit, typechecked and tested: all eight pass. Their `main` now has `release-0.3.1` merged, with the same tree, so each branch merges cleanly. Those branches aren't pushed. Until they are merged, each hire's main still carries the old kit, and `bump` refuses it.

## Taking on a new agent

A new agent (one the Wright built, or you did) is taken on from its clone, so the Steward's page lists it and its builds test and release it, with no hand-editing of settings.json (`src/employ.ts`):

```powershell
node %USERPROFILE%.stewardappsrccli.ts employ C:CodeAssayer --dry-run   # what it would add
node %USERPROFILE%.stewardappsrccli.ts employ C:CodeAssayer
```

Everything comes from the clone, on its branch as origin has it (`--branch`, main unless said), as the migration reads one: its id and name from its `manor-agent.json` (else its `src/app.ts`), its repository from origin, its kit parts from `kit.json` (none: listed, but off the kit's stages), and how to fill, test, version and release it from its files. What it can't find is named, to fill in on the Settings page. An agent, repository or clone the Steward looks after already is refused.

How it is released follows what Manor makes of it. Manor's internal staff (`staff.local.json`) are built and installed here (`npm run release -- --install`), never published, and so is one that neither announces itself nor is listed, until it does. ## Versions claimed up front

Two pieces of work started side by side on one repository each used to take "the next version" when they began, the same one, and found out when the second conflicted on its way in. Now whoever starts work asks the Steward for its version first (`src/claims.ts`):

```powershell
node %USERPROFILE%\.steward\app\src\cli.ts claim-version porter --branch claude/my-fix --for "the Run now button"
# Porter 0.4.22: yours. Set it in package.json, package-lock.json, src/app.ts.
```

It takes a repository's id, name or `owner/repo`: one in Settings, one Reeve found on this PC, the clone it runs in (by its origin), or the Steward's own; and hands out the next version no one has: above the version on its branch (main, usually) on GitHub, every release, every open PR's (by the version in its title), and every live claim. `--minor` for the next minor; `--json` for programs; `--by` says who asks (`claude` unless said). Claims go one at a time under a machine-wide lock, so two workers asking at once get two versions; the same branch asking again gets the same one. `claims` lists them (and `GET /api/versions`); `release-version <employee> <version>` gives one back.

A claim lives until its version is on the branch or overtaken by a release (the work landed), until it is given back, or for three days with no open PR that names it (its branch, or its version in a title); each round prunes them. One whose branch's PR is still open lives on though main passes it, so that PR can be re-versioned (below); a new claim for that branch takes its place. The Wright claims for each job before its worker starts, and gives the version back when no PR comes of it.

Nothing holds a PR for its version any more: whoever claimed one merges their own PR, and a build releases the version main carries. Versions merged out of order are the one thing to watch. A version merged below one already released isn't released ("v0.4.20 on its branch is below v0.4.22, released already: a version above it (claim-version) releases what is merged"): claim a new one, which comes above main's and every release, and the work that brings it releases what was merged.

**A PR stuck in the line is passed over** (Steward 0.36.247, `src/passover.ts`, from Steward#173). The open PR on a repository's lowest live claim is next in line, and every PR above it waits on it. Its claim is marked with what holds it (the owner first, a draft, a conflict, failing or unfinished checks, GitHub not knowing whether it merges, or only its author vouching and merging) and since when. The same head and the same hold for an hour is stuck: it is passed over, the next one up is next in line, and the PR is told. Once main passes its version, the Steward moves its claim to the next free version (one write to the claims ref, so no other PC hands that version out), merges main into its branch, sets that version in its version files, its changelog entry (`CHANGELOG.md`'s top, or its `changes/<version>.md`) and its title, and pushes. A PR whose version main passed before it was passed over (its authors merged out of order) is passed over at once. While it stays passed over, every round that finds main moved catches it up again. It is taken back into the line when its author pushes to it, or what held it ends (nothing but its author holds it, the owner labels it `owner-done`, or it is marked ready for review); where main passed it meanwhile, it is re-versioned once more. Then it is told to vouch and merge: the Steward merges nothing. A PR waiting for the owner first (labelled `owner-first`, or changing a migration) is marked and shown, and never told or pushed to until the owner labels it `owner-done`; nor is a draft or a PR that raises the kit too pushed to. The page (under the staff's table), an alarm and `claims` say "stuck since …, passed over (what holds it); will be re-versioned to x.y.z". Only the PC whose turn it is on the repository does any of it, and the marks live in the claims ref, so every PC shows the same.

Claims are shared by every PC that looks after a repository through `refs/manor/claims` in its remote, written by compare-and-swap, with a copy kept here so a build's stamp sees them. With the remote out of reach, a claim is made here alone, as before, and shared on the next round that reaches it; one another PC claimed meanwhile is marked on the page: take a new one for that work.

## The build pipeline

The Steward builds at set times (`src/pipeline.ts`): four a day to start with, 00:00, 06:00, 12:00 and 18:00, which Settings' **Build pipeline** tab changes. There is no switch to turn it off (Steward 0.36.40 to 0.36.62 had one, off by default; a settings.json that still keeps it builds all the same).

**Between builds** the rounds only look: nothing is released or rolled out, and nothing is merged by the Steward. Whoever writes a PR merges it once vouched (The rollout, "Merging and vouching"), and what it brings waits on the branch for the next build. On Castellan's own PC, a kit on the Steward's main with no release yet is tried on the agents meanwhile, a slice a round (Making a kit change), so the build finds it tried.

**At a build time a build begins.** Its rounds, for each repository it builds (the Steward's own among them, where this PC has the turn):

1. **Stamp main's unstamped entries** (`src/stages/stamp.ts`), where a repository keeps them in `changes/` (below). In a worktree of main's head, the version is set in the version files, each entry moves into `CHANGELOG.md` under its version, and the files are deleted, all in one commit on a branch of its own (`steward/stamp-<commit>`), which the Steward opens a PR for and merges itself ("Porter 0.4.2: version and changelog, stamped by the Steward"). It never pushes straight to main. A vouch that covered main's head is carried to the stamped commit, since only versions and changelogs changed. A stamp PR GitHub won't merge stays open: merge it yourself, and the next build releases it. Most builds have nothing to stamp, and make no worktree for it.
2. **Release the Steward's own** (Page and commands, "Its own releases"): main's new kit, once it passed its trial on every agent and the Steward's whole suite, then the Steward's own version.
3. **Roll the newest kit out** (every build, or only the day's first; never in an urgent fix's build): bumped, pushed and merged by the Steward itself (The rollout in a round). A kit on main still being tried keeps the build open, rather than sending every agent the kit before it, to be bumped again at the next build.
4. **Once nothing is left that settles within minutes, release each repository once** (`src/stages/mainbuild.ts`): main's newest commit, when it carries a version with no release yet. That very commit is tested first, once, and released only if it passes. Its pipeline's build commands run before its tests, and its release goes where its pipeline says (docs/PIPELINE.md). The test is skipped when a vouch covers the commit (a team account's `steward/tested` on it, or on the parent of a merge commit whose tree is the merge's own), or when the whole suite passed here on the same code. Otherwise its checks run here, in a worktree of their own (`<id>-main` in the work folder): only the tests the changes since the last release reach, unless Settings' `affectedTests` is off; a failure is run once more; a pass sets the vouch on that commit, so neither the next build nor the Assayer runs it again. A repository whose Settings give it no checks is released untested, as before builds tested main. A commit is tested once, kept by commit in `main-tested.json`, whatever happens to its release after: one that fails is a failed release (Alarms, below), and a new commit on the branch is tested afresh. A version below one already released isn't released (Versions claimed up front). Each release's notes bring every version merged since the repository's last release (a few side by side, those that sign one after another in a lane of their own); then Manor is told once.

A build that runs past its time (30 minutes unless Settings say otherwise, an hour at most) releases each main as it is, and a kit still being tried or rolled out waits for the next build. A build the PC slept through begins at the first round after it wakes, once. `pipeline.json` keeps the build under way and the last 30, each with the PRs of its own it merged (stamps and kit PRs), what it released and what failed, and where its time went (its phases with their starts and ends, `src/buildtimes.ts`: the page says in a line how long the last build took); `GET /api/pipeline` gives Manor the times, the next build and whether one is under way (Manor holds its installs while one is), and `releasesHere`: whether this PC releases any of the repositories it looks after (it holds the release turn of one, or no other PC holds it: `src/lease.ts`), so Manor offers Build now only on the PC that releases them.

The owner's override is **Build now**: `steward build [--employees a,b] [--to-customers]` at a console, which asks for "build" to be typed first and refuses without a console, or `POST /api/pipeline/build` with the page's token. `--to-customers` lets that build's releases out to customers at once instead of on their release day. Coding sessions never run it: their work waits for the next build.

An **urgent fix** doesn't wait (`src/stages/urgent.ts`): a commit on main whose changelog entry has a line starting `**Urgent fix:` (among the lines main added to `CHANGELOG.md` or `changes/` since its newest release) begins a build of its own at the next round, for its repository alone (the Steward's own too) and without the kit, and its release goes out to customers at once, as any urgent release does. Each head builds once: one whose release failed waits for a new commit or the next build. A repository with no release yet has no urgent build: its first release isn't an urgent fix's.

**Entries in `changes/`.** A repository with `changes/README.md` on its branch (`src/entries.ts`) has each piece of work write its changelog entry as a file of its own in `changes/`, leaving the version files and `CHANGELOG.md` alone, so two PRs side by side never meet in the same lines: `changes/<version>.md`, named by the version `claim-version` handed out, or `changes/<its branch as one word>.md`, which needs no version claimed (`claim-version` names the file). The build's stamp gives each `changes/<version>.md` its version, or the next free one when that one is released or claimed by other work meanwhile. It gives every branch's file merged since the last release one version: the one the branch waits to release, else the next free one above the last release (a minor step when a file's first line is `minor: true`), composed into one changelog entry: "Brings N changes: …", each section's bullets together, and "Before you update" saying "Nothing" only when none says anything else. An entry that says nothing, or whose heading names another version, isn't stamped: it waits for its author. In the Steward's own repository the kit has the same, in `kit/changes/`, with `kit\VERSION` and `kit.json`'s pin following it. Every employee the kit is rolled out to is put on it from Steward 0.36.248 (Manor since 2026-10-09): its kit bump adds `changes/README.md`, or, on the kit already, the rollout does on its own (above); only one worked with plain git stays as it was. The switch keeps work begun before it: a PR that set its version and wrote its `CHANGELOG.md` entry the old way still merges cleanly, since the kit's and the entries' files touch none of its lines, and while it is next in its version line (Versions claimed up front, above) main's entries wait for it (`oldWayFirst`), so they join the version it brings. One passed over is waited for no more.

## Several PCs

Each PC may run a Steward signed in to the same GitHub account. They elect one release PC per repository among themselves, through a ref in the repository's own remote, `refs/manor/release-pc`, with plain git on any host: no licence, no Exchequer ([docs/MULTI-PC.md](docs/MULTI-PC.md), `src/lease.ts`). Only publishing waits for the turn (a stamp, the Steward's merges of its own PRs, releasing, and the pushes of a refresh and a kit rollout); builds, tests, bumps and claims never do.

- A repository another PC has is left alone there, and the page says so ("Releasing for Clerk: done by DESKTOP-ABC"), with **Do it here** and **Keep it on this PC** (a pin, which other PCs leave alone unless it goes quiet for a day).
- Before each publishing act, one `ls-remote`: it acts only while the turn is still its own.
- A remote out of reach: the stage goes on as before there, and the page says releasing waits until this PC can reach it. A host that refuses the ref: this PC works alone there.

## Ports claimed up front

Only on Castellan's own PC. Every agent's page has a port of its own (its `src/app.ts`, and its Manor entry's `home` and `ping`), and Manor never offers an agent whose port another already has. New agents used to be given one by whoever started them, looking only at the clones on their PC: the Assayer took the Shepherd's 20707, and its role sat in Manor with no one to hire. Now a new agent's port is asked for first, as its version is (`src/ports.ts`):

```powershell
node %USERPROFILE%\.steward\app\src\cli.ts claim-port tallyman --branch claude/tallyman --for "the Tallyman"
# tallyman: port 21010, yours (a checkout serves on 31010). Set it in its src/app.ts (placeFor's port) and its Manor entry's home and ping.
```

It takes the agent's id, a new one included: no repository is needed yet. It knows every port in use: Manor's own (18585), Manor's staff, this PC's own staff (`staff.local.json`), the agents announced on GitHub, each employee's `src/app.ts` on its branch, and every live claim; and hands out the next free one of the agents' series (19090, 19191, … 20808, 20909, 21010, …) whose development twin (+10000) is free too. An agent that has a port keeps it; the same agent asking again gets the same port. `ports` lists them all, by whom and where it says so, and any two agents on one; `release-port <id>` gives a claim back. A claim lives until the agent's port shows in Manor's lists or its clone (it landed), until it is given back, or for 14 days.

Each round raises an alarm for two agents on one port, as their own sources say it, before either is installed ("shepherd and assayer have the same port, 20707"): Manor's summary already says so for installed ones.

## Install

The Steward installs itself, from a release, as every agent does. In a checkout of this repository:

```powershell
npm run release -- --install     # build a release, and install it
```

Or unpack a release zip anywhere (from GitHub, or `artifacts\steward\` after `npm run release`) and run `node src\cli.ts install` in it.

`install` copies the release to `%USERPROFILE%\.steward\app`; its data stays in `%USERPROFILE%\.steward`. It registers one sign-in task, `\Steward (<account>)\Home page` (each Windows account's in a Task Scheduler folder of its own), which runs `open` when you sign in, so the page comes back after a restart. Then it starts the page through that task and waits for it. A new install goes on duty. To update, install a newer release the same way.

**An update is on probation** (`src/safeinstall.ts`), since the builds release the Steward's own changes and Manor installs them with no one watching. Before anything changes, the version it replaces is copied whole to `app.prev`. Once the new one is in place and started, it must answer its ping as the new version, and keep answering, for 90 seconds, and its home page must render within them (asked on 127.0.0.1, so a network that is down can't fail it: Windows asks the network to name `steward.localhost`). If it doesn't (or the install itself fails once the new copy is in place), it is rolled back at once: its page ended, the new copy set aside as `app.unsafe-<version>` for a look, `app.prev` put back as `app` and started again. That version is flagged in `unsafe-updates.json` and refused, nothing changed, by every install after, so Manor's automatic updates give up on it after their few tries; it's an alarm at once. Dismissing that alarm (or `node src\cli.ts allow-update <version>`) is your look, and allows it again. A newer version installs as usual. An install that changed nothing (the old page wouldn't stop, say) flags nothing and is tried again; a first install, and `--no-start`, have nothing to go back to. Once the new version has held up, `app.prev` goes. An install that finds `app` missing and the installed copy in `app.old` (an earlier install's swap cut short by the PC going off) puts it back first, and updates it as any other. `--no-start` installs without starting it, and `--dry-run` says what it would do and changes nothing. `node %USERPROFILE%\.steward\app\src\cli.ts uninstall` ends the page process, deletes the task and removes `app`, with `app.prev` and `app.unsafe-<version>`; `uninstall --purge` also removes the data folder, with the work folder's worktrees (git then lists them as prunable).

A checkout is a development copy, and keeps out of the installed one's way: its data is in `%USERPROFILE%\.steward-dev`, its page is on port 29494, and `install` refuses to run from it. The installed copy has no `kit\` folder: it hands out the newest kit release, or the version named with `--kit`. The details, which every agent shares, are in Manor's INSTALLING.md.

The Steward needs git and `gh` on PATH (signed in, with rights to push and merge in the repositories it looks after: `gh auth login`) on this PC, and each repository's clone where Settings say. Without gh, whatever needs it says "gh isn't installed: install GitHub CLI, then run gh auth login".

## Page and commands

The page at http://steward.localhost:19494/ shows the kit the Steward hands out, the staff's table, a tick box for each employee (one that doesn't take the kit starts unticked) and a button for each stage (Bump, Push and Release; Release alone on a PC that doesn't release Castellan), the last stage's results and log, and **Settings**. It has no merge button: the Steward merges no one's PRs. While a stage runs, the page refreshes itself. The table is made again after each stage (from a fresh glance at GitHub), on **Refresh**, after a round when GitHub says something new of anyone, and when the page is opened more than 10 minutes after it was last made or checked while no rounds run. While the rounds run on duty, each one checks the table against its own glance, so opening the page asks GitHub nothing. `GET /api/ping` answers `{"app":"steward","name":"Steward","version":"0.8.6","pid":…,"running":true,"stoppedSince":null,"summary":"On duty.",…,"busy":false,"stage":null}`, `busy` while a stage runs. Like every agent page, it answers only to its own host names, and its buttons need the token from the page itself.

```powershell
node src/cli.ts bump [--kit <version>] [--employees a,b] [--kit-from <dir>] [--base <ref>]
node src/cli.ts push [--kit <version>] [--employees a,b]
node src/cli.ts release [--kit <version>] [--employees a,b]
node src/cli.ts round [--employees a,b]   # one round, as it runs by itself on duty (Run now)
node src/cli.ts staff [--json] [--no-fetch]
node src/cli.ts employ <its clone> [--branch <b>] [--dry-run]   # take on a new agent (Taking on a new agent)
node src/cli.ts build --dry-run <repo>   # each step a build of one repository takes by its pipeline, nothing run (docs/PIPELINE.md)
node src/cli.ts start            # on duty, and its page up (Manor's Start)
node src/cli.ts stop             # off duty (Manor's Stop); the page stays up
node src/cli.ts open             # make sure its page is up, without changing duty
node src/cli.ts shutdown         # end its page process
node src/cli.ts status [--json]  # on duty and working (exit 0) or not (exit 3); --json prints what Manor reads
node src/cli.ts serve            # the page in this window (what start and open run in the background)
node src/cli.ts install          # install this release (see Install); --no-start, --dry-run
node src/cli.ts uninstall        # remove the installed copy and its sign-in task; --purge also its data; --dry-run
```

`--hires` is the same as `--employees`. An unknown option is refused, and the stage doesn't run.

Its duty works as the hires' does, and its round is this: **between builds it looks; at a build it releases.** While it's on duty, and "Builds and releases by itself" is on in Settings, a round comes every 10 minutes ("A round every"), through the kit's `every()`, which pauses off duty. Between builds a round asks GitHub once (below), looks for an urgent fix on each main, and, on Castellan's own PC, tries main's new kit on the agents a slice at a time; while that trial goes on, the next round comes 2 minutes after it, at most three times in a row. It merges nothing and releases nothing. A build's rounds (The build pipeline, above) do this, in this order:

1. **Stamp** (`src/stages/stamp.ts`): main's unstamped `changes/` entries, each repository's and the Steward's own, put into its version files and `CHANGELOG.md` through a PR the Steward opens and merges itself (The build pipeline, above), so what is released carries its version and changelog.
2. **Its own releases** (`src/stages/self.ts`), kept apart from the employees', since the Steward's repository isn't an employee's: when the Steward's main on GitHub carries a kit version (`kit\VERSION`) with no `kit-v<version>` release, or a Steward version (package.json's) with no `v<version>` release, the build releases it as a person would, kit first: `node tools/kit.ts --from kit` and `node tools/kit-release.ts --publish` (`npm run kit-release -- --publish`, its kit filled first), then `npm run release -- --publish`. It reads both versions and the releases from its glance at GitHub (below), so it costs no call of its own. Each is made in a fresh worktree of the Steward's checkout (Settings' "The Steward's checkout") at that very commit of origin/main, in the work folder (`_steward-release`), never your working tree, and the worktree is removed after. Never from a tree with anything uncommitted in it (checked before publishing, and both scripts refuse one too), never a version already released (both scripts refuse that as well), and never a version that isn't above the newest release of its kind: that is left to you. A kit, which every agent takes, is released only once it has passed its trial on every agent at that commit (Making a kit change: one that fails holds the kit, and the Steward's version behind it, with an alarm of its own) and the Steward's whole suite has passed there (`src/stages/wholesuite.ts`): its PRs ran only the tests each change reached, so the Steward runs `npm run kit`, `npm run typecheck` and `npm test` whole first, in `_steward-whole` (`npm test`'s plain `node --test` run as node itself, between its pretest and posttest, so the checks pace sees node's test runner and runs only as many test files at once as its cap has room for), unless this PC already passed that very tree whole (a vouch or a test here whose change reached everything: `whole-passes.json`, by tree). A failure is run once more, then held like a failed release, unless no test failed both times, each passing in the other run: flaky, released all the same. On the Steward's page that whole suite runs beside the rounds, never inside one (0.36.45): the round that asks for it starts it as a job of its own, keyed by the kit's tag and commit, and goes on at once, the kit waiting; later rounds read what it came to (passed releases the kit, failed is held as above, still running waits, never with a second run beside it), and the round after it ends comes at once. A new commit on main stops it and starts one at the new commit; it ends, with every program it started, when the Steward stops, and one a Steward that is gone left running is ended at the next start (`whole-suite.json` keeps what it runs, and the page shows it while it runs). A round in a terminal (`steward round`) still runs it inside the round. A Steward version waits for its kit's release, and then for main's head to be tested here, as an employee's main is at a build, unless a vouch covers it (`src/stages/mainbuild.ts`); it isn't held for the whole suite. The Surveyor runs the whole suite on main once a day. A release carries only what is committed on main, never this PC's Settings or data, so an internal agent (the Wright) is never in anything it publishes. A release that fails is an alarm at once, and isn't tried again until a new commit lands on main (`self-failed.json`); a Steward version released tells Manor, as an employee's does (After a release, below), so Manor installs it within minutes. Settings' "Releases its own new versions" (`releaseSelf`) switches it off; a checkout whose origin isn't Settings' "The Steward's repository" is refused.
3. **The rollout in a round** (`src/stages/rollout.ts`): when the newest kit release is newer than the kit an employee's branch pins (kit.json at origin/<branch>), the employee has no other open PR that brings that kit already, and no bump to that kit failed at its branch's head, the build runs `bump` and then `push` for it, a few employees at a time (Settings' `parallel`), exactly as the stages do, and merges the PR at once, at the head it pushed: its checks passed in the bump, and no one else merges the Steward's PRs. The build releases it. A kit PR of the Steward's still open for an older kit gets the newer kit instead of a second PR beside it (the fold); one open at the kit rolled out already (a person's Push, or one GitHub wouldn't merge at once) is merged. On the Steward's page the bumps and pushes run beside the rounds, and the build releases once they end. One already on the kit (or ahead of it), one without a checkout or a kit.json, and one that doesn't take the kit are left alone; but one on the kit already and not on the build pipeline yet (no `changes/README.md` on its branch, and not worked with plain git) is given that file alone, in a PR of the Steward's own (`steward/pipeline-<commit>`, `src/stages/onpipeline.ts`, 0.36.248) that it opens and merges at once, as it does a stamp's: nothing is tested or released for it. A kit PR the rollout merges within the build is stamped at once, before the build releases. A bump that fails its checks, or a push that fails, is kept in `rollout-failed.json` with the kit and the head it failed at: an alarm at once, its worktree left for a look, and the rounds don't try that kit again until a new commit lands on the employee's branch, or a person presses Bump or Push (or runs `steward bump` / `steward push`). A newer kit is tried at once. A bump hands out the Steward's tools/kit.ts, the one released with the kit it carries. **While this Steward carries a kit older than the newest release** (the build released it in step 2, and Manor hasn't installed the Steward that carries it yet), each bump hands out the tools/kit.ts released with the new kit instead, read from the tag `kit-v<version>` in the Steward's own clone (0.35.29), so the kit goes out in the build that released it. Only when that can't be read does the rollout wait for Manor to install the Steward that carries the kit; a kit that waits that way for a day is an alarm. Settings' "Rolls out a new kit by itself" (`rollout`) switches it off: then Bump and Push run only when asked.
4. **Release**, once nothing is left that settles within minutes: every employee whose branch carries a version with no GitHub release yet is released from its branch, whatever kit it pins, as `steward release` would, that very commit tested first unless a vouch covers it (The build pipeline, above). Each waits for a passing release check of its commit from the Assayer first (Release, above): one the check holds says why, and is asked about again at the next build. A release that fails, its test among them, isn't tried again at the same commit (it's kept in `round-failed.json`): the round says so, and leaves it to you, the Release button or a new commit on the branch. A release that signs (an agent's native files, `kit.json`'s `native`; Manor's setup) is different: before it starts, the Steward checks that this PC can sign (the certificate and its key, and a trial signature). While it can't, with SimplySign Desktop not connected, say, the release waits: nothing is built, nothing fails, and the first build after the PC can sign releases it by itself (`signing-waits.json`). One that loses the key while it builds waits the same way. A version that is a new kit alone (`src/stages/kitonly.ts`, 0.36.70) is one whose only change since the employee's last release is the kit's bump: `kit.json`'s pin, the versions, its changelog entry, `tools/kit.ts`. The build releases it only when a file the kit changes is one the employee runs, or when the kit's changelog entry says it's urgent or names a fix for it (a bold line starting "Fix for <name>, <name>"). A file it runs is one reached from its own code under `src\` (not its tests): what that code imports, the kit files its text names, and the folders it reads. Only one such release goes out per employee a day (`kit-only-releases.json`). Otherwise the version waits, merged, and goes with the employee's next release of its own, whose notes bring its entry. The Release button releases it at once.
5. **Jobs**: an employee with an approve command and an installed copy in Settings (Reeve) has its jobs approved when they are what was merged. A job runs unattended only while its script is approved (Reeve pins its sha256), so an update that changes a script leaves the job waiting: that is how Reeve's `fast-forward`, which keeps every repository's `main`, `master` and release checkouts current, stopped after Reeve 0.4.1. Merged code counts as reviewed, so the round approves a job when its installed script is exactly the one in the commit the installed release was built from (`release.json`), and that commit is merged on the employee's branch on origin, whoever installed it (Manor's auto-update, the Steward, you). Never a development build (`release.json` says dirty), a release built from a commit that isn't merged, or a script that isn't what was merged: that is said once, and left to you. What it approved is kept in `jobs-approved.json`, so each script is approved once, and one you approved yourself stays quiet. The approve command reads the script again, so the round gives it the hash it checked, as `{sha256}`: Reeve's default, `jobs approve {job} --sha256 {sha256}` (Reeve 0.4.3 and later), approves that script or none, reading it once, so a script changed after its check is refused, not approved. For a command without `{sha256}`, the round checks afterwards that what it pinned (Reeve prints the sha256) is what was checked, and a script that changed in between, which can't be unapproved from here, is said loudly, once.
6. **The staff's pages** (`src/tend.ts`): every agent Manor employs that is on duty but whose page doesn't answer (its process ended, so its rounds don't run) has its page opened again through Manor's own Open (`POST /api/agents/<id>/open`, with Manor's page token, as its button), which runs the agent's open command and waits for its page. Read from Manor's `/api/state`: each role's holder and those on duty behind it, as Manor sees them; the kit's status says "on duty, page down" as stopped with no `since`. Its duty is never changed: an agent a person stopped stays stopped, and one Manor keeps off duty for Developer options, one Manor is busy with, one whose status Manor can't read, and the Steward itself are left alone. At most three tries while it stays down, five minutes apart, then one an hour; once the tries are spent, or Manor has no Open for it, it is an alarm until its page answers. Each try is a line in the round (`tend: …`); `tending.json` keeps the agents down and the last ones opened again, and the page shows them under **The staff's pages**. It needs only Manor's page (Settings, Alarms, "Manor's page"), never GitHub or a clone, and runs in every round, offline too. Settings' "Keeps the staff's pages up" (`tend`) switches it off.

**With no repositories to look after.** A Steward on a PC with no employee whose clone is here, and no checkout of its own (or Settings saying it doesn't release itself), has no GitHub work: its round asks GitHub nothing at all (no glance, no team, no kit releases) and is step 6 and the alarms, every few minutes on duty, as ever. Its page says so, in place of the stages, and its kit card is "The kit the Steward manages": it hands the kit to no one, and keeps it only to run on. With "Keeps the staff's pages up" off too, or no Manor named, it has nothing to do, and its page says that, with what to add. The same tend-only round comes on duty when "Builds and releases by itself" is off but "Keeps the staff's pages up" is on; Run now still does a whole round.

**Source control: GitHub isn't required** (`src/scm.ts`). Once an hour the Steward looks at what is installed on the PC (Git; the GitHub CLI, and whether it is signed in, from the token it keeps, never shown or stored; Mercurial, Subversion, Perforce and Plastic SCM, named but not worked with yet), kept in `source-control.json`. Settings' **Source control** offers only what was found (usually one) and says what it found. **Automatic** (the default) chooses for each repository: GitHub's way for a repository on GitHub (`owner/name`) where the GitHub CLI is signed in, everything below as it is; plain git for any other, on any host (`gitlab.com/group/app`, Azure DevOps, Bitbucket, a server or a shared folder), and for a GitHub one where the CLI isn't there. **Git** and **GitHub** choose one way for every repository. Castellan's own release machinery is GitHub's whatever is chosen. Worked with plain git, a repository has no PRs: whoever writes a branch lands it in the repository's branch, and the next build releases what is there, its newest commit tested here first (there is no host to carry a vouch). **When a branch is ready** (`whenReady`), the command the Steward once ran to land a claimed branch, is no longer run (0.36.124), and hidden. **After a release** (`whenReleased`), a command of its own in Settings (`src/stages/gitevents.ts`): runs in the clone once a release's tag is pushed, with `{tag} {version} {commit} {notesFile} {base} {repo} {checkout}`; a failure is a note on the release, which stands. Each command is split into words before its placeholders are filled, so a value stays one word and nothing reaches a shell; its glance is one `git ls-remote origin` in its clone (its branch's head and its `v<x.y.z>` tags, no GitHub call); a release is its release command, then an annotated `v<version>` tag at that commit, its message "<name> <version>" and the version's CHANGELOG.md entry, pushed to origin, never forced (one already on origin at that commit is left as it is; one at another commit is refused); Release it: tag is that tag alone; and a released version is one with its tag on origin. When every repository is worked with plain git (or, with none, the GitHub CLI isn't signed in), gh isn't run at all, not even for the team. Look after offers clones on any host: one whose origin isn't on GitHub (or with no GitHub CLI signed in) is offered without GitHub saying whether it can be pushed to, and the first tag pushed says. Everything asked of GitHub (pull requests, the vouch's commit statuses, releases, the Wright's issues) goes through a source host (`src/hosts/`): one interface with GitHub behind it, answering in GitHub's words, so other hosts with pull requests can stand in its place, each with its own signed-in tool. **GitLab** (`src/hosts/gitlab.ts`) is the first: Automatic works a repository on a GitLab (`gitlab.com/group/app`, or a host whose name says gitlab) with GitLab's way once the GitLab CLI (`glab`) is installed and signed in (`glab auth status`), else with plain git. Everything goes through `glab api` (REST v4, bodies as JSON from a file): merge requests stand for pull requests (the iid their number, `refs/merge-requests/<iid>/head` their head), merged with `sha` so only the head that was read merges; a merge request's files, line counts and checks come from its diffs and its head's commit statuses (a CI job is one); the vouch is a commit status; releases are GitLab releases. GitLab repositories have no glance: each stage asks of them on its own. With no team in Settings, the account `glab` is signed in as on each GitLab joins the team. Not yet on GitLab: downloading a release's files (an install after merge), and the Wright's issues. **Azure DevOps** (`src/hosts/azure.ts`) is the second: Automatic works a repository on Azure DevOps (`dev.azure.com/org/project/_git/app`, its SSH form, or `org.visualstudio.com`) with its way once the Azure CLI (`az`) is installed and signed in (`az account show`), else with plain git. Everything goes through `az rest` to the REST API (7.1), which takes a token for Azure DevOps from the signed-in account, so none is kept (on Windows the Steward starts the Azure CLI's own Python, as `az.cmd` does). A pull request's number is its id; Azure DevOps keeps no head ref for one, so its branch is fetched (a fork's isn't worked with); its files are its last iteration's (no line counts); its checks the statuses on it and on its head commit, the vouch among them as genre `steward`, name `tested`. It is completed with a merge commit at the head that was read (`lastMergeSourceCommit`). Azure DevOps has no releases: a release is an annotated `v<version>` tag made through the API, its message the title and the version's CHANGELOG.md entry. With no team in Settings, the account `az` is signed in as joins the team for its organization. Not yet on Azure DevOps: downloading a release's files, and the Wright's issues (Azure DevOps has work items). **Gitea and Forgejo** (`src/hosts/gitea.ts`, the same API on both) are the third: Automatic works a repository on a server the Gitea CLI (`tea`) has a login for (`tea logins list`: gitea.com, codeberg.org, a Gitea of your own) with Gitea's way, once tea is recent enough to have `tea api`; else with plain git. Everything goes through `tea api --login <that server's login>` (REST v1, bodies as JSON from a file with `-d @file`), so no token is kept; tea exits 0 whatever the server answers, so each request asks for the status line (`-i`) and an HTTP error is a failure. Pull requests are Gitea's own (`refs/pull/<n>/head`), merged with `head_commit_id` so only the head that was read merges; a draft is Gitea's "WIP:" title mark; a pull request's checks are its head's combined commit status; releases are Gitea releases, and their files are downloaded for an install after merging. Gitea's lists have no branch filter, so a branch's pull requests are looked for among the 200 most recently updated. With no team in Settings, the account tea is signed in as on each server joins the team. Not yet on Gitea: the Wright's issues (the adapter can file them; work.ts still asks GitHub). **Bitbucket Cloud** (`src/hosts/bitbucket.ts`) is the fourth: Bitbucket has no CLI that can merge (Atlassian's `twg` has no merge and, since 1.3.5, no raw API), so the Steward calls its REST API (2.0) with curl, with an Atlassian API token kept in this PC's git credential store for `api.bitbucket.org` (the account's email as its user name, the token as its password: Windows' Credential Manager, a generic credential named `git:https://api.bitbucket.org`). It reads the token with `git credential fill` (every prompt off, so a missing one fails quietly) only when it needs it, hands it to curl in a config file of its own that is deleted after, and never stores it or puts it on a command line. Automatic works a repository on bitbucket.org with Bitbucket's way once that token is there, else with plain git; Bitbucket Data Center stays plain git. A pull request's head is asked by its full hash (Bitbucket gives a short one); whether it merges, its files and its line counts come from its diffstat ("merge conflict" means it can't); its checks are its head's build statuses. Bitbucket keeps no ref for a pull request's head, so its branch is fetched (a fork's isn't worked with), and it merges with no head to match, so the head is checked just before merging and a merge Bitbucket finishes in the background is waited for. A build status doesn't say who set it, so the vouch's says so in its name (`steward/tested by <nickname>`); setting one needs write access to the repository. A release is an annotated `v<version>` tag made through the API. With no team in Settings, the token's account joins the team. Not on Bitbucket: downloading a release's files, and issues (its issue tracker is being retired).

**The PC kept awake for work** (0.36.45, kit 2.74.8's `awake.ts`). While the Steward runs an employee's checks (a build's test of main, a vouch, a bump, a kit trial, the whole suite beside the rounds), or makes a release, Windows doesn't sleep on its own; once the work ends it may again. A sleep you choose (Sleep, the power button, the lid) still happens, and the display still turns off. A round that only looks holds nothing, so the PC still sleeps between rounds with nothing to do.

**Code that already passed isn't tested again** (0.36.51, kit 2.77.0, `src/stages/standin.ts`). Before the Steward runs an employee's checks in a checkout with nothing uncommitted, a pass of exactly that code tree stands in, whatever commit it came from. It counts for a vouch, a build's test of main and the whole suite before a kit's release. It looks in three places, in order:

1. the Assayer's check of that folder (as a vouch always did);
2. this PC's own result for the tree (`work-results.json`);
3. with Manor's Other PCs on, the other PCs on the licence, asked through Manor (`GET /api/peers/result`, Manor 0.16.163 and later).

A pass from this PC or another is taken only when it is of the whole checks (never only the tests a change reached), for the same repository, under a day old, of every command Settings give the checks, and on the same Node.js major and OS (the kit's `whyNotPass`). The tree already pins the kit, the lockfile and the code; npm, git and the processor aren't matched. A failure here newer than the other PC's pass, and the checks run. A failure elsewhere never spares a run, and a 404 from an older Manor or agent is no pass. Nothing stands in for a kit under trial, for a run with settings of its own, or for a trial's look at an agent without the kit, whose point is this PC. The round's log says what stood in ("its checks passed on LAPTOP at 14:02, on exactly this code (tree 1a2b3c4): not run again"), a vouch's status says where ("… passed on LAPTOP at abc1234"), and a pass from another PC is kept here as that PC's, so Manor's Work page shows "passed on LAPTOP, not run again here". Every run of the checks now keeps the commands it ran and its Node.js and OS with its result, and answers `GET /api/peer/result` for another PC's Steward.

**A round asks GitHub once.** It begins with one `gh api graphql` query (`src/glance.ts`) for every employee at once: each repository's open PRs, for the staff's table; its branch's head commit; its releases, with the commit each tags; and the Steward's own releases, the kit's among them, with its main's head, `kit\VERSION` and package.json's version (one query per 5 employees, as GitHub gives a query 10 seconds; one it gives up on is asked again in halves). The branch heads it read are shared in Manor's `remote-heads.json`, so Reeve and the other agents skip their own `git ls-remote`. Between rounds the Steward's page keeps them fresh (`src/heads.ts`): every 5 minutes, unless a round's glance just read them, it reads every branch head of its repositories on GitHub, in one query of the heads alone (about a point of GitHub's 5,000 an hour); and 10 seconds after each merge it makes (a stamp's, a kit PR's), the merged repository's. So a build that takes long, as one with a kit trial can, never leaves them stale, and Reeve brings a clone's main up to a merge within a minute or so. Only while the Steward builds and releases by itself, on duty, and never into the budget's spare tenth. Between builds that glance is nearly all a round asks: each main is read for an urgent fix once at each new head. At a build its rounds look at every repository the build is for (fetch, read the version files and kit.json, stamp, test, release, roll out); a branch is fetched only when GitHub's head isn't the one the checkout has, and the releases run a few employees at a time (Settings' `parallel`).

**After a release**, the pages in Settings' "Told after a release" are POSTed as their own buttons would be (`src/upkeep.ts`: the token read from the page, the POST with it and no Origin): Manor's update check, so it installs the release within minutes rather than at its next look, up to 6 hours away. A build tells them once, when it ends, for everything it released. Each has 5 seconds; one that doesn't answer is only a line in the log.

A round with nothing merged, released, bumped, pushed or failed leaves no trace; one that did something is the last stage on the page, and a line in stages.log, as any stage is (the Steward's own releases are its row, "Steward", each line beginning "self:"; a stamp's lines begin "stamp:", a rollout's "rollout:"). A round passes while another round runs, or every stage's slot is taken; it runs beside any other stage. **Run now** (`steward round` in a terminal) does one round, on duty or not: between builds it only looks, as any round does. **Build now** builds (The build pipeline, above). `steward round --employees a,b` leaves the Steward's own releases out. Manor's employee card shows the rounds, from `/api/ping`. With "Builds and releases by itself" off, the stages run only when asked.

**Work the team can do goes to the Wright first** (`src/work.ts`; Settings' `fileWork`, on). An employee's bump to a new kit that failed its checks, its release that failed at a commit, and one of Reeve's alerts that is code work in an employee's repository (a new high or critical security advisory from dependency-health, a failed Maestro flow from maestro-runs, naming the employee) is filed as a `manor:work` issue in that repository: what failed, the end of its output with secrets taken out (`src/redact.ts`), the branch or commit, where the fix goes and what done means. A bump's fix goes on the employee's branch: `steward/kit-<version>` was never pushed, and the Steward makes it afresh from the branch once it moves. Each is filed once, by a hidden marker in its body (`<!-- steward:work:<id> -->`, per employee, kind and kit version or commit), at most three a day (`work-filed.json`), and only in an employee's repository the Wright's `GET /api/work` lists while it takes work, with gh signed in as one of its team; never in one of the PC's other projects the Wright helps with. Its alarm then waits 24 hours (`waitingHours`) from when it was filed, and is raised at once, saying why, when the Wright gets stuck on the issue (`wright:stuck`), its PR for it waits for a person (`wright:needs-you`), the Wright has no queue for that repository, or it couldn't be filed. The Steward's own releases, a push GitHub refused, and Reeve's other alerts (the NPU driver, the test phone, a job that crashed) stay alarms as before.

**Another Steward on the same repositories** (`src/strangers.ts`; only where `releasesCastellan` is on). On 2026-10-07 a second Steward, on another PC signed in to gh as the same account, merged this one's kit PRs seconds after they opened and released the staff all day, and this one's rounds only said "nothing new on GitHub". Now the Steward notes what it does itself as it does it, in `acted.json`: each PR it opens, each it merges, each release it makes, whichever stage or button ran it. Each round's glance shows its open `steward/…` PRs, which it watches with their head commit; one that is no longer open and whose head is now in its employee's branch (`git merge-base --is-ancestor` in the checkout here, no call to GitHub) was merged, and if not by this Steward, by someone else. One closed without merging is let go. The glance also shows each employee's releases: a new `v<x.y.z>` this Steward didn't make was made by someone else. The first round after an update only learns what is there, so an update raises nothing. Everything seen goes into one alarm, raised at once, that names the repositories, PRs and releases, and stays until a day after the last one seen. **Done by hand?** Mark it as yours, before or after: `node src\cli.ts mine <employee> <#pr | v<x.y.z>>`; it is never counted, and an alarm that named it drops it. Or Dismiss the alarm: what it names is taken as yours, and only a new one raises it again.

**One alarm for one crashed Reeve job.** The Surveyor reports a Reeve job that exited non-zero as the problem `agent.reeve.job.<job>`, and Reeve lists the same crash as an open alert whose `job` is that job. While Reeve's alerts name a job, the Surveyor's condition with the id `survey:agent.reeve.job.<job>` is dropped and Reeve's alert stands: his is at once, with the job's own words and link. When Reeve gives no answer, the Surveyor's stays. Reeve raises no notification of his own when Manor and the Steward are installed, so the Steward's is the one for his alerts.

An alarm is raised once, with one Windows notification for all raised in a round (clicking it opens this page), and stays at the top of the page under **Needs you**, and at `GET /api/alarms` for Manor, until its condition clears. **Dismiss** quiets one until it clears and comes back. The Steward never acts on an alarm by itself: it says what it saw and what to do. No alarm has a button that acts any more: the one that did, **Move it past the others**, went with the version queues (0.36.124).

**What passed here, for the Surveyor.** `GET /api/tested` lists, for each employee (and the Steward itself), the last 20 commits whose checks passed in one of the Steward's stages, newest first (`src/tested.ts`, `tested.json`): `{"at":…,"keep":20,"employees":{"porter":{"repo":"octocat/porter","tested":[{"commit":"<40 hex>","stage":"build","at":…,"branch":"main"},…]}}}`. `stage` is `bump` (the commit on `steward/kit-<version>`, before it is pushed), `build` (main's head, tested here before a build released it, where no vouch covered it) or `release` (the commit of the branch a release was built from and published). Records from before 0.36.124 may say `catch-up` or `merge`: a PR's head, tested before the Steward merged it. `branch`, `pr` and `version` are there where they are known. The Surveyor runs every agent's tests again once a day.

### The Wright's drafts

The Wright opens every pull request as a draft, so nothing it wrote merges without a look. Since 0.36.124 the Steward no longer looks at them, and marks none ready: whoever reviews one (a person, or the Bailiff where it is installed) marks it ready and merges it, as any PR. Settings' **The Wright's drafts** is no longer used.

The Bailiff's alarms stay (Alarms, above): unable to review, a review failing twice at one head, its page not answering. The Bailiff, like the Wright, is ours alone: an employee and an alarm source only where it is installed (`%USERPROFILE%\.bailiff\app`, or `BAILIFF_HOME`'s).

### Install scripts

A package's install script (its `preinstall`, `install` or `postinstall`, node-gyp for one with a `binding.gyp`, a git dependency's `prepare`) runs on this PC the moment npm installs it, before anything in the manor has looked at it. So every install the Steward makes (a shared set in `_modules`, a worktree's own, a release's, a refresh's, its own release) is guarded first (`src/installscripts.ts`):

- it reads the lockfile's `packages`, where npm records `hasInstallScript` for each package that has one;
- it runs `npm ci --ignore-scripts`, then `npm rebuild <name>` for the packages on Settings' **Install scripts allowed** alone (esbuild, unrs-resolver and fsevents to begin with: the ones the manor's own lockfiles carry);
- a package with a script that isn't on the list, or any git dependency, holds the work: nothing is installed, the stage says which package, and an alarm names it, its version, the repository and the script its registry entry says it runs (`npm view`, which runs none of its code). The hold is kept in `install-held.json` until the package is allowed or not seen for two days.

PRs are no longer held for their lockfile (0.36.124: the Steward merges none). So before you merge one whose `package-lock.json` brings a package new to the repository, or one with an install script that isn't allowed, look at it yourself: the guard above still stops the Steward's own installs of it, but not yours.

## Limits

- **It acts with your git and gh.** Pushes, PRs, merges and releases are yours. It never force-pushes, never touches your checkouts' working trees (it fetches, and adds and removes worktrees of them), and merges only the PRs it opens itself (a stamp, a kit rollout), at the head it pushed. It deletes only its own branches.
- **At its builds it releases and rolls out with no one asking.** What you merge to a repository's branch with a new version is released at the next build, its newest commit tested here first unless a vouch covers it: only as safe as those checks. A new kit is bumped, pushed and merged to every employee behind it: only as safe as the employees' checks, which the bump runs. Whatever is on the Steward's own main with a new version is released: merge to it only what you mean to publish. Switch "Builds and releases by itself" off in Settings to have it act only when asked, or `rollout` and `releaseSelf` for those two alone.
- **A kit PR GitHub won't merge at once stays open.** The next build's rollout merges it if it is still at the kit being rolled out, or gives it the newer kit; or merge or close it yourself.
- **A release is only as held as the Aletaster is here.** With no Aletaster, one off duty for Developer options, one that predates the tasting or doesn't answer, and for the Aletaster's own release, the Steward releases without a tasting, and says so.
- **An employee's checks run on this PC**, with the commands in Settings. A bump is only as good as its tests.
- **A kit version must be released before the employees pin it**, or a fresh clone of theirs couldn't fill its kit. `--kit-from` is for trials only.
- **tools/kit.ts reaches an agent with a bump**, so a change to it waits for the next kit version, and the old one does the filling until then: keep it small, stable and able to read the kit releases it will meet.
- **Its own PRs merge with no checks on GitHub.** The hires have no CI, so a kit or stamp PR's mergeability is the only check GitHub makes; the bump ran their tests before the commit, and a stamp changes only versions and changelogs.
- **Manor isn't an employee:** it is the next candidate to take the `node` and `web` parts (its settings-kit.ts and settings-panel.js are the kit's already).
- **Kit releases come from GitHub** for the installed copy. Without network it can still bump with `--kit-from`.

### The UI inventory

`npm run ui:inventory` (tools/ui-inventory.ts, ported from GamerNexus's apps/mobile script) asks what a page is made of, and flags what could be broken down and reused. It reads the Steward and its kit by default, and any agent's repository or Manor's with `-- --repo <folder>`: every page is moving to React, and the same questions apply in JSX as in template strings.

A **component** is a named function that writes markup (JSX, a tag in a string or template, or an `h('tag', …)` call as in settings-panel.js), and it **renders** the components it calls or puts in its JSX. TypeScript 7's own parser reads the code (`typescript/unstable/sync`, through a project of exactly the files read, made outside the repository), so a tag in a comment or a `<branch>` in usage text isn't counted. Tests, builds, `src\kit\` (the Steward's kit, copied in) and build-time tools (`art\`, `scripts\`, `tools\`) are left out.

- **Repeated markup**, the leading indicator: an element with the same tag and classes (`span.muted`) written out 4 times or more. A bare `<td>` and SVG drawing don't count.
- **Largest components:** over 60 for a component, 150 for a page, where size is lines, or characters / 100 when that's more (a line here can run to hundreds of characters).
- **File-local** components, those **never used** (the kit's exports serve every agent: check them before deleting), what each file **writes by hand** per component, the **most reused**, and the **render tree** from each page (a route's, or a React root's `render(<App/>)`) down to the core: the kit's page.ts, or a `components/ui` folder.

Every finding is a question, not a defect. Reports go in the Steward's `docs\` (git-ignored): `UI-INVENTORY.md` and `.html`, or `UI-INVENTORY-<repository>.*` for another, which is never written to. `-- --tree` prints the tree, `-- --check` says whether the report is current, `-- --strict` fails on any finding, and `-- --ci` only on a component past 140 or a page past 320.

The Steward takes its own kit the way a hire does: `kit.json` pins it (the `node` and `web` parts, which bring the core and spec), and `npm run kit` fills `src\kit\` from this checkout's `kit\` (`--from kit`). The dotnet tests restore Jint and xUnit from nuget.org (`kit\test\nuget.config`), whatever this PC's NuGet config lists. The tests make fake employees with git in temporary folders, with gh standing in, and serve tools/kit.ts a kit release from a local server; nothing reaches GitHub but one lookup of a release that isn't there. A checkout runs as the development copy, in `%USERPROFILE%\.steward-dev` on port 29494.
